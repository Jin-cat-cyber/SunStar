# 定步长物理自测（DEBUG_PHYS）—— 设计与判据技术报告

> 涉及文件：`src/PhysicsSelfTest.h`（header-only，UTF-8 带 BOM）、`src/SpaceShip22.A.cpp`、`OpenGL_Learning/OpenGL_Learning.vcxproj`
> 被测对象：`Spaceship::AdvanceFixed` / `FixedUpdate` / `RenderPosition` / `RenderHeading`（见 `src/Spaceship.h`）
> 配套报告：《定步长物理与渲染插值_数学原理与代码实现技术报告》
> 定位：把"定步长 + 渲染插值"的正确性做成**可执行判据**，每次 Debug 启动自动回归。

---

## 0. 结论速览

| 测试 | 证明什么 | PASS 判据 | FAIL 意味着 |
|---|---|---|---|
| **T1** 帧切分无关 | 物理状态只由**步数**决定，与"这些步被打包成几帧"无关 | 位置差、四元数差**逐位为 0** | 物理里混进了帧相关量（`FixedUpdate` 被改回用整帧 `dt`、步内用了 `deltaTime`） |
| **T2** 卡顿钳制 | 单帧超大 `dt` 不会引发补算风暴 | 单帧 3 s 只跑 **29–30 步** | `MAX_ACCUM` 没生效 → 会跑 360 步（飞船瞬移 + 卡住） |
| **T3** 插值有效性 | 渲染用的是**插值姿态**且插值真的在平滑 | 插值后抖动 **< 0.05**，未插值 **> 0.5**（理论 ≈1.20） | 抖动 ≈1.20 说明渲染用原始物理位置；打印 `nan` 说明一帧一步都没跑（余数丢失） |
| **T4** 步进器不变式 | `AdvanceFixed` 的步数、$\alpha$、残差三项不变量 | 总步数 ≈ `帧数·dt/h`（±1）、$\alpha<1$、残差 $<h$ | 总步数偏低 ⇒ 余数没跨帧保留；$\alpha\ge1$ ⇒ 循环边界写错 |

## 1. 设计目标

1. **常驻而非一次性脚本**：接入成本只有 2 行，Release 下零成本，于是没有理由只让它活在一次调试里；
2. **与生产代码共享实现**：T2/T3/T4 直接调用生产用的 `Spaceship::AdvanceFixed`，测的不是"抄一份的影子逻辑"；
3. **不依赖 GL 与窗口**：可以放在 `main` 第一行，在 `glfwInit()` 之前跑完（微秒级），崩溃/黑屏时也能拿到结论；
4. **不污染全局状态**：全部使用局部 `Spaceship` 实例，绝不碰 `Globals.h` 里的 `ship`；
5. **完全可复现**：抖动帧时间用固定种子的线性同余发生器生成，任何机器、任何次数结果一致。

## 2. 模块结构

### 2.1 为什么是 header-only

```cpp
#pragma once
#include <cstdio>
#include "Spaceship.h"

namespace phys_test {
#ifdef DEBUG_PHYS
    ... 全部实现（inline）...
#else
    inline void Run() {}          // Release：退化成空函数
#endif
}
```

- **不动 `.vcxproj`**：新增 `.cpp` 必须用 VS"添加现有项"登记，漏登 → `LNK2019`，重复登记 → `LNK2005`（本项目两个坑都踩过）。header-only 完全绕开；
- **多 TU 安全**：AGENTS.md 允许头文件里放 `inline` 函数（类内定义的成员函数同理是隐式 inline）；
- **自 gate**：真实实现包在 `#ifdef DEBUG_PHYS` 内，`#else` 分支提供一个空的 `inline void Run()`，于是**调用点不需要任何 `#ifdef`**：

```cpp
int main()
{
    phys_test::Run();     // L72：Release 下什么也不做
    glfwInit();
    ...
}
```

### 2.2 开关：`DEBUG_PHYS` 只加在 Debug 配置

```
vcxproj L121（Debug）  : _DEBUG;_CONSOLE;%(PreprocessorDefinitions);DEBUG_PHYS
vcxproj L137（Release）: NDEBUG;_CONSOLE;%(PreprocessorDefinitions);
```

好处：不用在源码里改开关、不会忘记关；Release 构建里既无输出也无代码。

### 2.3 编码：UTF-8 带 BOM

文件含中文注释，而工程内编码是混的（`SpaceShip22.A.cpp` 是 UTF-8、`Spaceship.h` 是 GBK/936）。带 BOM（前三字节 `EF BB BF`）能让 MSVC 无条件按 UTF-8 解析，避免 `C4819` 或中文被当 GBK 误读。**新建文件时建议在 VS 里用"另存为 → 编码保存 → UTF-8 带签名 - 代码页 65001"**。

### 2.4 与生产代码的覆盖关系

| 测试 | 步进方式 | 为什么 |
|---|---|---|
| T1 | **手写**步进循环（内联累加器） | 需要把输入**按物理步序号**注入，`AdvanceFixed` 内部循环无法插入回调 |
| T2 / T3 / T4 | 直接调 `ship.AdvanceFixed(...)` | 覆盖生产路径本身（累加器语义、$\alpha$、边界） |

这个分工是有意的：T1 管"物理是否只依赖步数"，T2/T3/T4 管"累加器与插值机制"，两者互补且不重复。

## 3. 四项测试的判据与依据

### 3.1 T1：帧切分无关（逐位一致）

**做法**：输入脚本由**物理步序号**驱动（`Script(s, step)`，每 120 步换一节，6 秒一循环，覆盖前进/偏航/滚转/俯仰/垂直/滑行），然后用 6 种帧时间模式各自推进到**恰好 1200 步**（= 10 秒 @120Hz），比较终态。

| 帧模式 | 帧时间 | 预期帧数 | 预期墙钟 |
|---|---|---|---|
| 120 fps | $1h$ | 1200 | 10.0000 s |
| 60 fps | $2h$ | 600 | 10.0000 s |
| 30 fps | $4h$ | 300 | 10.0000 s |
| 144 fps | $1/144$ | 1440 | 10.0000 s |
| 240 fps | $1/240$ | 2400 | 10.0000 s |
| 抖动 | $0.5h \sim 8h$ | ≈283 | ≈10.0 s（参考值） |

**判据**：以 120 fps 那一行为基准，其余各行的

- 位置最大分量差 `dp == 0.0f`
- 四元数最大分量差 `dq == 0.0f`

**为什么浮点相等比较在这里是合法的**：两次运行的 `FixedUpdate` 被调用次数相同、调用内部运算序列逐条相同（步长恒为常量 $h$，累加器不参与物理），因此结果是同一段代码在相同输入下的**位级重放**；帧切分只影响"何时调用"，不影响"调用内容"。

**为什么墙钟列只是参考**：抖动模式的平均帧时间大于 $h$，凑满 1200 步所耗墙钟会略有出入；判据只看 `dp/dq`。

### 3.2 T2：卡顿钳制

```cpp
Spaceship s; float accum = 0.0f, alpha = 0.0f;
const int steps = s.AdvanceFixed(accum, 3.0f, alpha);   // 单帧 3 秒
```

**期望步数** = $M/h = 0.25 / (1/120) = 30$（不钳制则 360）。

**判据放宽到 29–30**：`float` 下 $0.25 - 30 \times (1/120)$ 的舍入残差可能落在 $h$ 的两侧，30 或 29 都算正确。写死 `== 30` 会得到一个随机失败的测试。

### 3.3 T3：插值有效性（抖动度量）

**做法**：先把飞船直线加速到满速并保持（无转向 ⇒ `Forward()` 恒定 ⇒ 纯匀速直线），然后用 **144 fps**（与 120 Hz 不同相）跑 2 秒 = 288 帧，分别统计

- `pI = ship.RenderPosition(alpha)`（渲染路径该用的）
- `pR = ship.position`（物理原始位置，即"没做插值"的对照）

的逐帧位移 $d = |p_k - p_{k-1}|$，取抖动度量

$$\text{jitter} = \frac{\max d - \min d}{\operatorname{mean} d}$$

**推导理论值**（144 fps，$dt/h = 0.833$）：累加器以 6 帧为周期跑 5 步（3.1 节之外的纯算术：残差按 $1/144$ 递增、每步扣 $1/120$，6 帧回到起点）。于是

- **未插值**：位移只在"这一帧跑了步"时发生，$d \in \{0,\ v h\}$；287 个样本共 240 步 ⇒ $\operatorname{mean} d = \frac{240}{287}vh = 0.836\,vh$，$\min = 0$，$\max = vh$
  ⇒ $\text{jitter} = 1/0.836 \approx \mathbf{1.20}$
- **插值后**：$\Delta R = v\,dt$ 恒定（§2.4 的定理）⇒ $\max \approx \min \approx \operatorname{mean}$ ⇒ $\text{jitter} \approx \mathbf{0}$

**判据**：`jitterInterp < 0.05` 且 `jitterRaw > 0.5`。理论值 1.20 与 0.00 距判据都有很大余量。

**判读提示**：若 T3 打印 `抖动=nan`，说明 288 帧里一次 `FixedUpdate` 都没发生（$\operatorname{mean}=0$ 导致 $0/0$）——这正是"累加器余数丢失且 $dt < h$"的典型症状。

### 3.4 T4：共享步进器不变式

对 `240 / 120 / 60 / 30 fps` 四档各跑 600 帧，检查三项：

| 不变量 | 期望 | 破坏它说明 |
|---|---|---|
| 总步数 | $\approx 600 \cdot dt/h$（±1） | 余数没跨帧保留（总步数系统性偏低） |
| $\alpha$ 上界 | $< 1$ | `while` 边界写错（用了 `>` 或漏了减法） |
| 残差上界 | $< h$ | 同上 |

各档预期：

| 帧率 | 每帧步数 | 600 帧总步数 | $\alpha$ 上界 |
|---|---|---|---|
| 240 fps | 0 ~ 1 | 300 | 0.5 |
| 120 fps | 1 | 600 | ≈0 |
| 60 fps | 2 | 1200 | ≈0 |
| 30 fps | 4 | 2400 | ≈0 |

T4 是四项里**信息量最大**的一项：它同时覆盖"余数跨帧保留"（总步数）与"边界正确"（$\alpha$、残差），且不需要任何输入脚本。

## 4. 关键设计决策

| 决策 | 理由 |
|---|---|
| 输入脚本按**步序号**驱动，而不是按时间/帧 | 让"帧切分"成为唯一变量；否则不同帧率下输入时刻不同，逐位比较无从谈起 |
| 抖动帧时间用固定种子 LCG（`seed = 20260915u`） | 可复现；能覆盖"某帧一步都不跑"的路径（$dt = 0.5h$） |
| 比较用**最大分量差**而非向量长度 | 长度会把"某个分量错得很离谱"平均掉；分量差对逐位断言更直观 |
| 用 `Spaceship` 局部实例 | 不污染 `Globals.h` 的全局 `ship`；可以放在 `main` 第一行 |
| 不用 `assert` 而用 `printf` + `PASS/FAIL` | 需要看到**数值**（步数、抖动值），而不仅是"过/不过"；也避免 Debug 断言打断启动 |
| Release 用空函数而不是整块 `#ifdef` 调用点 | 调用点保持一行、永远可编译 |

## 5. 实战战果：它抓到了"值传递"bug

**现象**：改为定步长后飞船移动"一卡一卡"。

**根因**（详见配套报告 §7.1）：`AdvanceFixed` 的第一个参数被写成 `float accum`（值传递），调用方的 `physAccum` 永远为 0，**每帧余数被丢弃** ⇒ 帧时间在 $2h$ 附近抖动时，步数在 1 步/2 步之间交替 ⇒ 渲染速度在 1×/0.5× 之间来回跳。

**若自测当时已接线，两项会直接报警**：

| 测试 | 该实现下的表现 | 结论 |
|---|---|---|
| T4 · 240 fps 行 | 每帧 $dt = 0.5h < h$ ⇒ **一步都不跑**，总步数 = 0，理论 300 | **FAIL**（总步数偏低，直指"余数没保留"） |
| T3 | 288 帧同样一步不跑 ⇒ 位移全为 0 ⇒ $\text{mean}=0$ ⇒ 抖动打印 `nan` | **FAIL** |

**教训**：接入只花 2 行（`#include` + `phys_test::Run()`），当时却只 include 了、没调用 —— 于是这份自测从"守门员"退化成了"事后验证工具"。**先接线，再改逻辑。**

启动时控制台会输出一段以 `=========== 定步长物理自测 (DEBUG_PHYS) ===========` 开头的报告，逐项看四行 `>>> Tx: ...`：

| 输出 | 含义 | 处置 |
|---|---|---|
| `>>> T1: PASS（物理只由步数决定，与帧切分无关）` | 物理确定性成立 | — |
| `>>> T2: PASS` | 卡顿保护生效 | 若显示 360 步 ⇒ 检查 `MAX_ACCUM` 是否还在被使用 |
| `>>> T3: PASS（期望 插值<0.05 且 未插值>0.5）` | 插值机制正常 | 打印 `nan` ⇒ 帧内一步未跑；插值值 ≈1.2 ⇒ 渲染没走 `RenderPosition` |
| `>>> T4: PASS` | 累加器语义与边界正确 | 看哪一档的"总步数"偏离理论值即可定位 |

T1 的明细表里，除基准行外每行都应显示 `源差 = 0.000000000`（`dp`/`dq` 两列）。

## 7. 运行与开关

1. **编译配置**：VS 项目属性 → C/C++ → 预处理器 → 预处理器定义 → **Debug 配置**加 `DEBUG_PHYS`（Release 不加）；
2. **调用**：`main` 第一行 `phys_test::Run();`（不需要包 `#ifdef`）；
3. **关闭**：从 Debug 配置里删掉 `DEBUG_PHYS` 即可，源码不用改；
4. **成本**：约 5000 次 `FixedUpdate` + 数十行输出，微秒级，肉眼一个闪烁都不到。

## 8. 局限与可扩展

**已知局限（诚实说明）**：

- **T3 只验证"插值机制"，不验证"调用点是否用了它"**：它直接调 `RenderPosition(alpha)`，因此"相机/阴影/前向 PBR 三处是否都换成插值姿态"仍要靠代码审查（对应配套报告的"同一渲染帧唯一姿态"铁律）。要自动化这一条，得在真实主循环里做断言；
- **不覆盖真实主循环的步频**：真实帧率、`vsync`、GPU 负载都不在这些离线用例里。可选的补充是**运行时探针**（每秒钟打印"步/秒、每帧步数区间、$\alpha$ 上界、插值前瞻"），把 `SpaceShip22.A.cpp:383` 的 `(void)stepCount;` 换成一段汇总输出即可；
- **不是基线回归**：目前只做"不变式断言"，没有把结果与历史基线比对。若以后要做，可把终态量化后取哈希、落盘比对（注意浮点格式与编译器开关必须固定）。

**可扩展方向**：

1. **运行时探针**（成本最低、覆盖"真实主循环"这一空白）：`步/秒 ≈ 120 ± 1`、`每帧步数` 随帧率变化但总步频恒定、`累加器剩 < 8.33 ms` 恒成立；
2. **相机平滑项**：把 `followSmooth * dt` 的线性 `mix` 换成 $1-e^{-k\,dt}$ 时，可加一条"不同帧率下相机滞后量一致"的判据；
3. **未来物理扩展**（重力/碰撞）接入后，T1 的价值会立刻放大：它保证"同一段输入 ⇒ 同一轨迹"，这正是调参和故障复现的前提。
