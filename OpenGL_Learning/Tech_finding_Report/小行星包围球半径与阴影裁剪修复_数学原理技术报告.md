# 小行星包围球半径与阴影裁剪修复 —— 数学原理技术报告

> 涉及文件：`src/SpaceShip21.0.cpp`、`src/Procedural.cpp`、`src/Procedural.h`
> 症状：屏幕边缘（尤其四角）偶尔有小行星"还有一部分在画面内就被剔除、突然消失"；阴影侧同源。

## 1. 问题背景：两条剔除路径共享同一个几何量

本工程对 5 万颗小行星实例做两级剔除：

- **A 路径（可见性 → G-Buffer）**：相机视锥剔除，判据 `SphereInFrustum(fp, c, r)`；
- **C 路径（投射者 → 阴影）**：光源可见性剔除，判据 `CanCastVisibleShadow(fp, lightPos, c)`，通过的实例再按 `AssignCasterFaces` 分到立方体深度图的若干个面。

两条路径都依赖同一个几何量：**每个实例的包围球 $(c,r)$**，其中

```
c = model[3]                 // 实例矩阵的平移分量 = 模型空间原点
r = rockMeshBoundR * s       // 网格包围半径 × 实例缩放
```

**整个调查的逻辑起点**（后面反复用到）：

> 若包围球**真的包住**几何体，且球-平面判据是**保守**的（只剔除"整球在外"），
> 那么"物体还有一部分在视锥内却被剔除"在数学上**不可能发生**。

因此一旦看到 pop，就必须去查 $(c,r)$ 或判据本身，而不是去调 margin 或怀疑视锥矩阵。

## 2. 数学原理 A：视锥平面与球-平面判据

### 2.1 从 VP 矩阵提取 6 个平面（Gribb–Hartmann）

裁剪空间内的可见区域由 6 个半空间定义（$-w\le x,y,z\le w$）。把 $VP$ 的第 $i$ 行取成四维向量 $\mathbf{r}_i$，则

```
left   = r3 + r0      right  = r3 - r0
bottom = r3 + r1      top    = r3 - r1
near   = r3 + r2      far    = r3 - r2
```

每个平面写成 $\mathbf{n}\cdot\mathbf{x}+d=0$，**内部**满足

$$\mathbf{n}\cdot\mathbf{x}+d \ge 0$$

### 2.2 归一化：必须用法线的三维长度

要让 $\mathbf{n}\cdot\mathbf{x}+d$ 具有**有符号欧氏距离**的量纲，必须除以

$$\|\mathbf{n}\|=\sqrt{a^2+b^2+c^2}$$

而**不是**四维向量的长度 $\sqrt{a^2+b^2+c^2+d^2}$。工程里 `ExtractFrustum` 做的正是前者（正确）。

### 2.3 球-平面判据与"保守性"

球心到平面的有符号距离为 $D=\mathbf{n}\cdot\mathbf{c}+d$，半径为 $r$，则

$$\text{整个球在平面外侧} \iff D < -r \iff \mathbf{n}\cdot\mathbf{c}+d+r<0$$

所以判据写成

```cpp
if (glm::dot(glm::vec3(plane), c) + plane.w + r < 0.0f) return false;   // 只有"整球在外"才剔除
```

那个 `+ r` 就是**保守性的全部来源**。几何上，这等价于把视锥与一个半径 $r$ 的球做 **Minkowski 和**（视锥向六个方向各外扩 $r$）：

$$\mathcal{F}_r=\{\,x : \operatorname{dist}(x,\mathcal{F})\le r\,\}$$

**推论（本报告最重要的一条）**：

$$\text{物体部分可见} \;\Longrightarrow\; \text{球与}\ \mathcal{F}\ \text{相交（且沿该平面} D\ge -r\text{）} \;\Longrightarrow\; \text{不会被剔除}$$

即：**只要 $r$ 正确，pop 不可能出现。** 反过来说，任何 pop 都直接指向 $r$（或包围体）错误。

## 3. 数学原理 B：变换后的包围球半径

### 3.1 精确上界 = 最大奇异值

物体空间半径 $\rho$ 的球，经仿射变换（线性部分 $A$，即模型矩阵左上 $3\times3$）后变成椭球，其半轴长为 $\rho\,\sigma_i(A)$（$\sigma_i$ 为奇异值）。因此**能包住它的球半径**为

$$r=\rho\cdot\sigma_{\max}(A)$$

必须用 $\sigma_{\max}$（最大拉伸方向），因为最坏方向决定边界。

### 3.2 便宜的上界与"正好精确"的情形

| 情形 | $\sigma_{\max}(A)$ | 廉价算法 |
|---|---|---|
| $A=sR$（**均匀缩放 × 旋转**） | $s$ | **任取一列的长度**（$=\|\!sR_{:,j}\!\|=s$ 精确） |
| $A=SR$，$S=\mathrm{diag}(s_x,s_y,s_z)$ | $\max(s_x,s_y,s_z)$ | 显式取最大缩放分量 |
| 一般 $A$（含 shear） | — | $\sigma_{\max}\le\|A\|_F$（Frobenius），或 $\sigma_{\max}\le\sqrt{\|A\|_1\|A\|_\infty}$ |

> ⚠️ **注意**：对一般矩阵，"最大列长"**不保证**是 $\sigma_{\max}$ 的上界。反例：
> $A=\begin{pmatrix}1&1\\1&1\end{pmatrix}$，列长均为 $\sqrt2\approx1.414$，而 $\sigma_{\max}=2$。
> 同理，非均匀 $A=SR$ 时列长一般**小于** $\sigma_{\max}$：
> $S=\mathrm{diag}(3,1,1)$、$R=R_z(45^\circ)$ 时 $\|col_0\|=\sqrt{5}\approx2.236<3$。
> 因此"取三列最大值"只在**均匀缩放 × 旋转**下等价于 $\sigma_{\max}$——本项目的小行星恰好属于这一族；若将来混入 shear 或非均匀缩放，应改用 $\max(s_x,s_y,s_z)$ 或 Frobenius 上界。

### 3.3 本项目的实例矩阵

`RocksModelMatricesInit` 里：

```cpp
model = glm::translate(model, offset);
model = glm::scale(model, glm::vec3(scale));   // S = scale · I
model = model * rotation;                       // M = T · S · R
```

线性部分 $A=\text{scale}\cdot R$，$R$ 为旋转矩阵（列向量是单位向量），所以

$$\|A_{:,j}\|=\text{scale}\cdot\|R_{:,j}\|=\text{scale}\qquad(j=0,1,2)$$

**三列长度都精确等于 `scale`**。这就是正确公式的数学依据：

```cpp
float s = glm::max(glm::length(glm::vec3(model[0])),
          glm::max(glm::length(glm::vec3(model[1])), glm::length(glm::vec3(model[2]))));
```

### 3.4 $c$ 与 $r$ 的配对前提

`rockMeshBoundR = max‖v.Position‖` 是"**模型空间原点到最远顶点**"的距离，因此必须与"模型空间原点"配对，而这个原点经实例矩阵映射后正好是平移分量 `model[3]`。配对成立的前提是**绘制时不再施加额外变换**——已核实 `Model::Draw`（`Model.cpp:9-12`）与 `PbrModel::Draw`（`PbrModel.cpp:9-12`）都只是逐 mesh 调用 `meshes[i].Draw(shader)`，没有节点变换/缩放。

## 4. 数学原理 C：为什么"取矩阵对角线"会漂

### 4.1 错误公式

原代码：

```cpp
float s = glm::length(glm::vec3(model[0][0], model[1][1], model[2][2]));   // ← 错
```

它算的是 $A$ 的**对角线三元素构成向量的长度**。对本项目 $A=\text{scale}\cdot R$：

$$s_\text{bad}=\sqrt{\sum_i A_{ii}^2}=\text{scale}\cdot\underbrace{\sqrt{\sum_i R_{ii}^2}}_{=:\,f}$$

**关键**：对旋转矩阵，$f=\sqrt{R_{00}^2+R_{11}^2+R_{22}^2}$ **不是常数 1**，从而

$$\boxed{\;r_\text{used}=f\cdot r_\text{true}\;}$$

### 4.2 $f$ 的一般取值范围（Rodrigues）

绕单位轴 $\mathbf{n}$ 转 $\theta$，记 $c=\cos\theta$，则 $R_{ii}=c+(1-c)n_i^2$（反对称部分对角线为零），于是

$$f^2=\sum_i\big[c+(1-c)n_i^2\big]^2=3c^2+2c(1-c)+(1-c)^2\sum_i n_i^4$$

取 $\mathbf{n}=(1,1,1)/\sqrt3$（即 $\sum_i n_i^4=\tfrac13$）：

$$f^2=\frac{(2c+1)^2}{3}\quad\Longrightarrow\quad f=0\ \text{当}\ c=-\tfrac12\ (\theta=120^\circ)$$

**所以 $f=0$ 在一般情形下确实可达**（绕 $(1,1,1)$ 轴转 $120^\circ$ 是轴置换，对角线全零）；$f$ 的取值范围是 $[0,\sqrt3]$，其中 $f=\sqrt3\approx1.732$（$R=I$）意味着半径**虚高 73%**（安全方向，只是少剔几颗）。

### 4.3 本项目具体角度的 $f(a)$

本项目的复合旋转为 $R=R_x(\theta_x)R_y(\theta_y)R_z(\theta_z)$，其中

$$\theta_x=0.5a,\quad \theta_y=0.3a,\quad \theta_z=0.2a,\qquad a=\texttt{rotAngle}=\texttt{rand()\%360}$$

令 $c_x=\cos\theta_x$ 等，逐项展开 $R_x(R_yR_z)$ 得对角线：

$$\begin{aligned}
R_{00}&=c_yc_z\\
R_{11}&=c_xc_z-s_xs_ys_z\\
R_{22}&=c_xc_y
\end{aligned}$$

$$f(a)=\sqrt{R_{00}^2+R_{11}^2+R_{22}^2}$$

> 注意：一般情形能取到 0（§4.2），但**这一组特定角度比例取不到 0**——它的最小值是 $0.4516$。

### 4.4 数值扫描结果（$a=0\ldots359$ 整数，与 `rand()%360` 一一对应）

```
min f = 0.4516  (a = 359)        连续极限 ≈ 0.4473
max f = 1.7321  (a = 0)          // R = I，半径虚高 73%
E[f]  = 1.0012                   // ← 平均值几乎正好是 1
```

分布（360 个取值）：

| $f$ 区间 | 比例 | 含义 |
|---|---|---|
| $[0.00,0.50)$ | 2.5% | 半径缩到不足一半 |
| $[0.50,0.60)$ | 3.9% | — |
| $[0.60,0.70)$ | 16.1% | 残留 10%~22%，**可察觉** |
| $[0.70,0.80)$ | 11.9% | 残留 5%~9% |
| $[0.80,0.90)$ | 11.9% | 残留 2%~5% |
| $[0.90,1.00)$ | 19.4% | 残留 <2%，基本看不出 |
| $[1.00,1.74)$ | 34.2% | 半径偏大 → **只会少剔，无视觉问题** |

即：**约 46% 的实例半径偏小**（$f<0.9$），其中 **22.5% 缩到 0.7 以下**，最坏 0.45 倍。

> $E[f]\approx1.0012$ 解释了一个重要现象：**任何聚合统计都看不出问题**（平均半径、可见实例总数、`[cull] visibleCount` 全部正常），问题只存在于单实例分布的尾部。

## 5. 现象与数学的对应关系

### 5.1 "还有一部分在画面内就被剔除"的定量解释

球心越过平面 $f\cdot r_\text{true}$ 之后（此时球才"整球在外"），仍留在视锥内侧的部分是**球冠**，高度

$$h=r_\text{true}-f\,r_\text{true}=(1-f)\,r_\text{true}$$

它在屏幕上的投影面积占比（圆被距圆心 $d=fr$ 的弦切下的**小**弓形）：

$$\text{residual}(f)=\frac{\arccos f-f\sqrt{1-f^{2}}}{\pi}$$

| $f$ | 0.4516 | 0.50 | 0.57 | 0.6475 | 0.6725 | 0.866 | $\ge1$ |
|---|---|---|---|---|---|---|---|
| 残留投影占比 | **22.3%** | 19.5% | 15.8% | 11.9% | 10.7% | 2.9% | 0% |

最坏情形残留约 **22%**——对于一颗屏幕上占幅很大的近处小行星，这是一块相当醒目的画面，主观上就是"还有一多半在那儿"。

### 5.2 为什么感觉"突然消失"

剔除是**布尔判断**，没有渐变：一帧之前还在画，一帧之后整个实例从 `gVisible` 消失。$f$ 偏小只是让这个布尔翻转**提前**发生，并不会让它变缓。

### 5.3 为什么集中在屏幕的四个角

- 角上**同时贴近两个平面**：只要满足"对任一平面整球在外"就整体剔除，角上的实例有两次机会触发；
- 角上的小行星通常是**离相机最近、屏幕占幅最大**的一批，同样的 22% 残留，绝对面积最大、最扎眼；
- 反之画面中央的球即使 $f$ 很小，也很难同时满足"离某个平面 $>f r$"，所以几乎看不到。

### 5.4 为什么"非常非常少，几乎察觉不到"

可察觉需要三个条件**同时**成立：

1. $f$ 足够小（$\lesssim0.7$，即约 22.5% 的实例）；
2. 该实例此刻恰好位于屏幕边界；
3. 它在屏幕上足够大（离相机足够近）。

三者同时命中的概率很低 ⇒ 任意一帧只有零星几颗。这也解释了为什么这个 bug 容易被"看漏"，直到专门盯着边缘才发现。

### 5.5 阴影侧的两种表现

- **面桶分配**：$r$ 偏小 ⇒ $\alpha=\arcsin(r/L)$ 偏小 ⇒ `AssignCasterFaces` 的判据 $\cos(45^\circ+\alpha+1.5^\circ)$ 变紧 ⇒ 跨立方体面边界的那几颗只被分进**一个**面桶 ⇒ 相邻面的深度图里缺它 ⇒ **阴影缺一条**（与 A 路径是同一批 `rotAngle`）。
- **C 判据是点测试**（见 §6）⇒ 球心射线没进视锥但球体压在视锥边界上的实例被**整颗**丢弃 ⇒ **阴影整块消失**。

## 6. 数学原理 D：C 判据从"点"到"球"

### 6.1 点判据的推导

从光源出发、穿过点 $p$ 的射线 $x(t)=\text{lightPos}+t\,\mathbf{d}$，$\mathbf{d}=\widehat{p-\text{lightPos}}$。代入内部条件 $\mathbf{n}\cdot x+w\ge0$：

$$t\,(\mathbf{n}\cdot\mathbf{d})\ \ge\ \underbrace{-w-\mathbf{n}\cdot\text{lightPos}}_{=:\ \text{num}}$$

- $\mathbf{n}\cdot\mathbf{d}>0$ ⇒ 下界 $t_\text{enter}=\max(t_\text{enter},\ \text{num}/\mathbf{n}\cdot\mathbf{d})$；
- $\mathbf{n}\cdot\mathbf{d}<0$ ⇒ 上界 $t_\text{exit}=\min(t_\text{exit},\ \text{num}/\mathbf{n}\cdot\mathbf{d})$；
- 射线穿过视锥 $\iff t_\text{enter}\le t_\text{exit}$；
- **$p$ 能挡住可见表面** $\iff$ 存在 $t>L_p$ 使 $x(t)$ 在视锥内 $\iff t_\text{exit}>L_p$。

这就是 `return Lp < tExit;` 的由来（早期写成 `tEnter > Lp` 是方向反了，会导致视锥内的小行星被判为"投不出阴影"）。

### 6.2 缺陷：只代入球心

球的截面被压成一条线 ⇒ 只判别"过球心的那根线"。一个球可以**整块压在视锥边界内侧**，而过球心的射线在视锥外（或 $t_\text{exit}<L_p$）⇒ 该实例被整颗丢弃。

### 6.3 修正：视锥按 $r$ 做 Minkowski 膨胀

把内部条件换成膨胀后的 $\mathbf{n}\cdot x+w+r\ge0$，等价于

$$t\,(\mathbf{n}\cdot\mathbf{d})\ \ge\ \text{num}-r$$

于是**唯一改动**是

```cpp
float num = -pl.w - glm::dot(n, lightPos) - r;   // 视锥六个面按 r 外扩
```

其余逻辑（含 `|denom|<1e-6` 的平行分支）自动保持一致，因为 `num` 里已经带了 $-r$。

### 6.4 为什么这是"安全方向"

从光源看，球在参数 $t$ 处的截面半径是 $r\cdot t/L_p$；对 $t>L_p$ 有

$$\frac{t}{L_p}r>r \quad\text{不成立}\ \Rightarrow\ \text{真实光锥比 } r\text{ 圆柱更窄}$$

用半径为 $r$ 的圆柱（即视锥外扩 $r$）做判定，**必然得到一个超集** ⇒ 不会漏掉任何真正能投影的投射者，代价只是每帧多画几颗。

方向性上这也正好与实际后果对齐：

| 判据过严（漏球） | 判据过宽（多留球） |
|---|---|
| 阴影整块消失 —— **可见 bug** | 多画几颗实例 —— 仅性能 |

## 8. 三条可复用结论

1. **保守判据 + 正确包围体 ⇒ 不可能出现"部分可见却被剔除"。** 遇到 pop，先查包围体，不要先加 margin、也不要先怀疑视锥矩阵。
2. **包围球半径必须取 $\sigma_{\max}$ 量级的上界。** 均匀缩放 × 旋转时"任取一列长度"是精确值；**绝不要用对角线元素**这类"看起来像缩放"的量——它是旋转的随机函数。
3. **判据必须按被裁剪体的尺度加宽，且加宽方向必须保守**（视锥外扩 / $t_\text{exit}$ 变大）。加宽只会多画，收窄会丢画面。

## 9. 注意事项

1. **3 参与 4 参 `CanCastVisibleShadow` 的重载是有意保留的**（老版本 17.A / 18.0 / 19.0 / 19.A / 20.0 仍以 3 参形式调用）。
   ⚠️ **不要给 4 参加默认参数** `float r = 0.0f`：那会让调用 `CanCastVisibleShadow(fp, lp, c)` 同时匹配两个候选、且转换序列完全相同 ⇒ **ambiguous，编译报错**。要么保持现状（两个重载），要么"删 3 参 + 加默认值"，二选一。
   ⚠️ 老版本那 5 处仍是**点判据**：一旦把某个门控打开当基线，§6.2 的缺陷会随之回归。
2. **临时自测块 `SpaceShip21.0.cpp:1335-1340`**：`fMin` 算而未打印；`static` 变量会跨调用累积。修好后 $f=s/\text{scale}$ 应**恒等于 1.0**，所以 `[radius]` 一行都不该出现——可以留作回归警报，建议用 `#ifdef DEBUG_CULL` 包住并补上循环外的打印。
3. **`AssignCasterFaces` 理论上可能返回 0 个面**：任意方向到最近立方体轴的夹角可达 $54.7^\circ$（面对角线方向），一旦超过 $45^\circ+\alpha+1.5^\circ$ 就没有任何轴被选中，该实例将完全无阴影。本场景安全（所有投射体都在 $+Z$ 轴 $28.3^\circ$ 以内，离 $45^\circ$ 还有约 $15^\circ$ 余量）；若将来把投射体扩散到其他方向，应加兜底：`if (n == 0) { faces[0] = 最近轴; n = 1; }`。
4. **非均匀缩放的下界风险**：见 §3.2 的反例。"三列最大值"仅在均匀缩放 × 旋转下等于 $\sigma_{\max}$。
5. **`shadow_far = 1000` 的深度截断**属于同类的"边界截断"问题（不是球包围问题）：离光源超过该距离的投射者会被深度裁掉而失去阴影。可用 `max‖c − lightPos‖` 的量级自查。

## 附录：$f(a)$ 扫描脚本（Node，可复现 §4.4）

```js
const D = Math.PI / 180;
function f_of(a) {
  const u = 0.5 * a * D, v = 0.3 * a * D, w = 0.2 * a * D;   // θx, θy, θz
  const R00 = Math.cos(v) * Math.cos(w);
  const R11 = Math.cos(u) * Math.cos(w) - Math.sin(u) * Math.sin(v) * Math.sin(w);
  const R22 = Math.cos(u) * Math.cos(v);
  return Math.sqrt(R00 * R00 + R11 * R11 + R22 * R22);
}
let mn = 9, mx = -9, s = 0;
for (let a = 0; a < 360; a++) { const f = f_of(a); mn = Math.min(mn, f); mx = Math.max(mx, f); s += f; }
console.log("min", mn.toFixed(4), "max", mx.toFixed(4), "E[f]", (s / 360).toFixed(4));
// 剔除瞬间的残留投影面积占比
const residual = f => f >= 1 ? 0 : (Math.acos(f) - f * Math.sqrt(1 - f * f)) / Math.PI;
// 输出：min 0.4516  max 1.7321  E[f] 1.0012
```
