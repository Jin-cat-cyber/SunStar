# 第 1 段 · 状态存在哪

代码在 `src/Globals.h` 的"战术折跃（warp）状态"一节：

```cpp
struct WarpState
{
    bool      active = false;               // 时间线正在运行
    float     tau = 0.0f;                   // 自按键起算的秒数
    float     cooldown = 0.0f;              // 距下次可用还剩的秒数
    glm::vec3 delta = glm::vec3(0.0f);      // 折跃位移向量 D_eff * f_hat
};
inline WarpState gWarp;

inline float WARP_DISTANCE = 100.f;
inline float WARP_COOLDOWN = 6.0f;
inline float WARP_MIN_DIST = 10.0f;
inline bool tKeyPressed    = false;
```

## 为什么放在全局

折跃状态有三个消费者：主循环（推进时间线并执行传送）、相机（跟随平移）、投影矩阵（FOV 冲击）。放进 `Spaceship` 只有物理侧读得到，另外两个要绕一圈才能拿到。反过来，物理侧只需要**一个方法**（`WarpTo`），所以折跃并不是"把玩法塞进飞船类"，而是"一个视觉事件借用飞船的一次重定位"。

`inline WarpState gWarp;` 这一行有三层含义叠在一起：

1. C++17 的 `inline` 变量允许在头文件里定义变量，多个翻译单元各自 include 也只存在一个实体，不会 LNK2005。
2. 变量名必须带 `g` 前缀。这不只是习惯：同一作用域下 `namespace warp` 与 `inline WarpState warp;` 会让 MSVC 报 `C2757`。因此分工固定为——纯函数进 `namespace warp`，状态进 `gWarp`。
3. 成员全是标量与向量，没有指针，因此是平凡可复制的，放在静态存储期没有初始化顺序问题。

## `active` 与 `tau` 的分工

`active` 回答"时间线在不在跑"，`tau` 回答"跑到第几秒"。`tau` 只在 `active` 时才有意义；时间线结束时主循环把 `gWarp.active` 置假并 **把 `tau` 归零**，而 $\mathrm{sample}(0)$ 会让五个通道全部为 0、`solid` 为 1——也就是"常规舰体"这个状态。**停机态因此不需要任何特判**，这正是把效果做成"一条以 τ 为参数的曲线"的回报：特判是"忘了重置某个 uniform"这类 bug 的温床。

`tau` 是**唯一时钟**。所有视觉量都是它的函数，工程里不存在第二个计时器。好处有三：慢放只需缩放单帧增量（同一条参数化曲线被拉长，几何关系一点不变）；掉帧不会让各通道失步；"钉住一帧"这种操作才有意义（只有一个时间轴可以被钉）。

## 被删掉的 `teleported` 字段

`WarpState` 里有一个注释掉的 `bool teleported;`。传送是**单帧事件**，标志由 `advance` 的返回值带出（`warp::Step::teleport`），不放进跨帧状态。做成字段就必须有人负责置位与清零，于是有两个失效模式：忘了置位（传送不发生）、忘了清零（连传两帧、位移翻倍）。这个字段在第一版实现里真的漏写过 `= true`，症状是"舰体缩小了一下还在原地"——一个用眼睛很难定性、只能靠断言抓的错误。

## 另外几个常量的用意

- `cooldown` 存的是**倒计时**不是时间戳，在传送那一帧被设成 `WARP_COOLDOWN`。存倒计时就不需要在别处保存"上一次折跃发生在第几秒"，也就没有跨系统的时间基准问题。
- `delta` 在**按下 T 的那一帧**算好并冻结，传送时用 `ship.position + gWarp.delta`。所以落点方向由按键瞬间的朝向决定，之后 `heading` 再怎么变都不影响这一跳。注意位移是加在**传送那一帧**的位置上的，不是按键那一帧的位置。
- 三个可调量故意写成 `inline float` 而不是 `constexpr`：它们是阶段 7 要反复调的参数，`constexpr` 改一次就要整体重编。其中 `WARP_MIN_DIST` 目前一处引用都没有，是阶段 6（落点合法性）留的坑位，不是死代码。
- `tKeyPressed` 是上升沿锁存：`glfwGetKey(...) == GLFW_PRESS` 在按住 T 的每一帧都为真，没有锁存就会每帧重新触发。

# 第 2 段 · 缓动地基

```cpp
inline float clamp01(float x)
{
    return x < 0.0f ? 0.0f : (x > 1.0f ? 1.0f : x);
}

inline float smoothstep01(float x)          // s = x^2 (3 - 2x)
{
    x = clamp01(x);
    return x * x * (3.0f - 2.0f * x);
}

inline float quintic01(float x)             // phi = 6x^5 - 15x^4 + 10x^3
{
    x = clamp01(x);
    return x * x * x * (x * (x * 6.0f - 15.0f) + 10.0f);
}

inline float trap(float tau, float r0, float r1, float f0, float f1)
{
    const float up   = smoothstep01((tau - r0) / (r1 - r0));
    const float down = smoothstep01((tau - f0) / (f1 - f0));
    return up * (1.0f - down);
}
```

## `clamp01` 为什么手写三元式

`Warp.h` 有意不 include glm（文件头写明了这条约束），所以用不了 `glm::clamp`。相比 `fminf/fmaxf`，三元式还有一个好处：第三个分支是**原样返回**，落在范围内的值一个 bit 都不动，而 `min(max(x,0),1)` 走的是两次函数调用。边角情况也要知道：NaN 会从两个比较里穿过去，所以不能给 `r0 == r1` 这种输入（$(\tau-r_0)/(r_1-r_0)$ 在 $\tau$ 恰好等于该值时是 $0/0$）。

## `smoothstep01` 是 C1 而不是 C2

记 $s(x)=x^2(3-2x)$，则 $s(0)=0$、$s(1)=1$、$s'(x)=6x(1-x)$，所以 $s'(0)=s'(1)=0$，两端拼接处一阶导连续，是 C1。但 $s''(x)=6-12x$，于是 $s''(0)=+6$、$s''(1)=-6$：**起点处二阶导是从 0 跳到 6 的**。这条性质决定了 σ 的使用范围——被作用量若是位移，这个跳变会被看成"起步一顿"；若是**强度**（亮度、混合权重、通道权重），二阶导的跳变眼睛分辨不出来，用 C1 足够，还省一次乘法。

## `quintic01` 为什么恰好是五次

要同时满足"两端值、两端一阶导、两端二阶导"共六个条件，最少需要六个系数的多项式，也就是五次；条件正好六个，所以这个五次多项式是**唯一解**。验算：$\varphi'(x)=30x^2(x-1)^2$，$\varphi''(x)=60x(x-1)(2x-1)$，因此两端一阶、二阶导全为零，是 C2。

为什么要 C2：位移的二阶导就是加速度，加速度在起步与停止的瞬间跳变，观感就是"顿一下"。所以凡是被当成**运动**读的量一律用 $\varphi$（拉伸量、预备退距、FOV 冲击、抖动包络、骨架生长），而被当成**明暗**读的量用 $s$。另外 $\varphi'(x)=30x^2(x-1)^2\ge 0$ 说明它单调，且中间比线性更陡（$\varphi(0.5)=0.5$、$\varphi(0.25)\approx 0.104$），也就是"慢起、慢收、中间快"。

## `trap` 的两段相乘

`up` 把 $[r_0,r_1]$ 归一化后过 $s$，得到"从 0 平滑升到 1"；`1 - down` 是下降沿取补，得到"从 1 平滑落到 0"；两者相乘。因为 $s$ 是 C1、乘积仍是 C1，所以整个梯形在四个拐角处都光滑。

**关键性质**：当 $r_1\le f_0$ 时，平台段上 $up\equiv 1$ 且 $down\equiv 0$，峰值**恰好等于 1**。这就是通道表那条硬性约束的来历——一旦某行写成 $r_1>f_0$，两段斜坡会在 $(f_0,r_1)$ 上相乘，那里处处小于 1，峰值达不到 1，而且**不报错**，只会看到那一段莫名其妙偏暗。另外两个写法都被排除了：`up - down` 会出负值且平台不再是精确 1（要额外 clamp，而 clamp 又会造出平台，就是静止态伪影那类问题的同类）；`min(up, 1-down)` 在两段交叉处一阶导不连续。

# 第 3 段 · 五个通道与 `sample`

```cpp
//        r0     r1     f0     f1
//  u_c   0.00   0.40   0.45   0.62   电流
//  u_v   0.45   0.60   0.62   0.68   白化与拉伸
//  u_w   0.62   0.70   0.95   1.08   线框
//  u_a   0.98   1.05   1.10   1.22   实体化
//  u_g 不用梯形，见下方 flash（它需要单侧尖点）。

inline Channels sample(float tau)
{
    Channels k;
    k.c = trap(tau, C_R0, C_R1, C_F0, C_F1);
    k.v = trap(tau, V_R0, V_R1, V_F0, V_F1);
    k.g = flash(tau);
    k.w = trap(tau, W_R0, W_R1, W_F0, W_F1);
    k.a = trap(tau, A_R0, A_R1, A_F0, A_F1);
    k.solid = clamp01(1.0f - k.v - k.w);
    return k;
}
```

（上表是 `T_CHARGE=0.45 / T_VANISH=0.20 / T_WIRE=0.35 / T_APPEAR=0.25` 时的取值，只作对照；代码里四个通道的十六个数全部写成相对量，见操作表。）

## 两套时间：叙事分段与通道区间

文件头的四段标称时长（蓄能 0.45、隐没 0.20、线框 0.35、实体化 0.25）是**给人读的叙事分段**；通道表里的 $[r_0,f_0]$ 才是**给代码用的实际权重区间**。两者故意不重合：每个通道都越出自己所属的分段，让相邻效果搭接。若通道都严格活在本段内，段与段之间会出现"两个通道都接近 0"的空档，画面上读起来是一次卡顿。

搭接的位置有整齐的规律：**前一个通道开始淡出的时刻，等于后一个通道开始上升的时刻**——`C_F0 = V_R0`、`V_F0 = W_R0`，而 `W_F0` 与 `A_R0` 刻意差 0.03（让材质赶在实体化之前先起一点）。整个 1.25 秒里任何时候都至少有一个效果在起作用。

## 逐行读参数

每行四个数含义固定：$r_0/r_1$ 是上升段的起点与到顶时刻，$f_0/f_1$ 是下降段的起落时刻，于是 $[r_1,f_0]$ 是强度恒为 1 的平台。

- `u_c`：升 0.40、平台 0.05、降 0.17。平台短，观感是"快速亮起、慢慢退"，蓄能到顶后一直维持到舰体开始烧白才交棒。
- `u_v`：三段都最短（0.15 / 0.02 / 0.06），因为它要卖"瞬间烧穿"。到顶时刻 0.60 正好是闪现开始上升的时刻。这里有一个容易误读的点：**τ\* 那一帧舰体看不见，不是白化保证的**（那一帧 `u_v` 已经掉到 0.5 了），而是几何被完全剥除（`geoFront = FRONT_HI`）保证的。
- `u_w`：升 0.08、**平台 0.25（最长）**、降 0.13。线框是抵达段的主体形态，必须待得最久。
- `u_a`：升 0.07、平台 0.05、降 0.12，在 1.22 归零，给钉帧留出 0.03 s 余量。

## `sample` 的职责边界

它是**唯一**把标量 τ 翻译成一组权重的地方。同一帧里舰体 PBR pass、电流外壳 pass、蓝图与线框 pass、全屏闪现 pass 读的都是**同一个 `wch`**，不存在"舰体已经白化了、外壳还满亮"这种时间错位，因为没有任何一个 pass 自己去算时间。想调整节奏只改这张表，不用碰绘制代码；反过来说，哪天有人在某个 pass 里直接写 `trap(tau, ...)`，这套一致性就破了。

`Channels` 的默认值也不是随手写的：`c/v/g/w/a` 默认 0、`solid` 默认 **1**。因为 τ = 0 必须表示"常规舰体"，而常规舰体的实体度当然是 1。

## `solid` 为什么长这样

深度 pass 不能做半透明，所以"投不投影"只能是二值的：先算一个连续的实体度，再用门限二值化。减的是 `v` 与 `w` 这两个：`v` 到顶意味着舰体已经是一团过曝的白光，此时影子若还在，就会露馅；`w` 到顶意味着舰体已被拆成线条，同理不该投出实心影子。

数值上可以验算：`v` 在 τ = 0.60 恰好到 1，而那时 `w = 0`，所以 `solid` 归零——**白化到顶的同一瞬间停止投影**。之后 `w` 起来时 `solid` 已经被夹在 0；直到返程 `w` 掉回 0.5 以下（约 τ = 1.03）才重新变正。`clamp01` 在这里不是装饰：`v` 与 `w` 在 $[0.62,0.68]$ 上重叠，$1-v-w$ 有可能为负。

主循环里实际用的是 `solidNow = wch.solid * (1 - geoFront)`。乘上这一项是因为真实溶解是**逐像素 discard**，`v` 与 `w` 都不知道前沿走到哪了；不乘就会出现"影子已经是一整艘船、舰体还看不见"。代进返程算一下：那时 `solid = 1`，门限 `solidNow > 0.5` 等价于 `geoFront < 0.5`，对应 τ ≈ 1.10，即**材质重建过半之后影子才回来**。

# 第 4 段 · `flash` 的单侧尖点与 `advance` 的钉帧

```cpp
inline float flash(float tau)
{
    if (tau <= TAU_STAR)
        return clamp01((tau - FLASH_RISE) / (TAU_STAR - FLASH_RISE));

    const float x = (tau - TAU_STAR) / (FLASH_END - TAU_STAR);
    if (x >= 1.0f) return 0.0f;
    return std::pow(1.0f - x, FLASH_POW);
}
```

## 上升段为什么故意写成线性

把 τ 归一化后，上升段的导数恒为

$$\frac{d}{d\tau}\frac{\tau-\text{FLASH\_RISE}}{\text{TAU\_STAR}-\text{FLASH\_RISE}}=\frac{1}{0.05}=+20\ \text{每秒}$$

是常数，不随 τ 变。这正是要的：亮度以均匀速率冲上去。若上升段改用 $s$ 或 $\varphi$，导数在峰值处会趋近 0，也就是**在到达最亮之前先变成一条越来越平的水平线**，"最亮的时刻"就成了一个模糊区间，闪现变成日出。这一条与第 2 段不矛盾：$s$ 与 $\varphi$ 的零导数端点是给**运动**用的，而闪光要读成**事件**，事件的两端本来就该是硬的。

## 峰值处导数不连续是特征

上升段在 τ\* 处的左导数是 +20；衰减段 $(1-x)^p$ 的导数是

$$\frac{d}{d\tau}(1-x)^p=-p(1-x)^{p-1}\cdot\frac{1}{\text{FLASH\_END}-\text{TAU\_STAR}}$$

在 $x=0$ 处代入 $p=2.2$、衰减段长度 0.09，得 $-2.2/0.09=-24.44$ 每秒。左右导数不同，所以整条曲线在峰值处**不是 C1**，那里是一个尖点。C1 要求峰值两侧导数都为 0，也就是要求顶部有一段平坦——那就是"亮度到顶后停一会儿"，不是闪。**$s$ 与 $\varphi$ 消灭折角，`flash` 保留折角**，因为前者作用在运动与强度分布上，后者作用在时间事件上。

## 衰减段为什么必须 $p>1$

其一，**先快后慢**：斜率绝对值是 $p(1-x)^{p-1}/(\text{FLASH\_END}-\text{TAU\_STAR})$，因为 $p-1>0$，它在 $[0,1)$ 上单调递减，从 24.4 降到 0。代一个数：衰减半程 $x=0.5$ 处剩余亮度 $0.5^{2.2}=e^{2.2\ln 0.5}\approx 0.218$；若用线性衰减，同一时刻还剩 0.5。

其二，**末端自然落地**：$x\to 1$ 时值与斜率同时趋近 0，衰减段结束在一阶导为零处，不会在 `FLASH_END` 上出现"从 −11 突然变 0"的折角。所以这一段是"起点硬、终点软"。

## 两个容易漏掉的细节

`clamp01(...)` 不只是防止超过 1：它同时让 $\tau\le\text{FLASH\_RISE}$ 时**恒等于 0**，这是"τ = 0 即静止态"能在 `g` 通道上成立的原因。

`if (x >= 1.0f) return 0.0f;` 是一道 **NaN 闸门**。τ 超过 `FLASH_END` 之后 $1-x$ 是负数，而 $\mathrm{pow}(\text{负数},2.2)$ 返回 NaN；NaN 会顺着 `flashAmount` 进到色彩里，症状是整屏变黑或花掉，而且离肇事点很远。

精度上还有一件小事：τ 恰好等于 `TAU_STAR` 时走上升段分支，返回的是 $\mathrm{clamp01}\big((\text{TAU\_STAR}-\text{FLASH\_RISE})/(\text{TAU\_STAR}-\text{FLASH\_RISE})\big)$——分子分母是**同一个表达式**，所以商逐位等于 1。这就是"存在一帧 $u_g=1$"能精确成立的根据。

```cpp
struct Step
{
    float tau = 0.0f;
    bool  teleport = false;   // 本帧执行传送，且仅本帧
    bool  finished = false;   // 时间线已越过 T_TOTAL
};

inline Step advance(float& tau, float frameDt)
{
    Step s;

    float dt = frameDt < 0.0f ? 0.0f : frameDt;
    if (dt > DT_MAX) dt = DT_MAX;
    dt *= TIME_SCALE;

    if (tau < TAU_STAR && tau + dt >= TAU_STAR)
    {
        tau = TAU_STAR;          // 本帧精确钉在峰值上
        s.tau = tau;
        s.teleport = true;
        return s;
    }

    tau += dt;
    s.tau = tau;
    s.finished = (tau >= T_TOTAL);
    return s;
}
```

## 四行准备工作的顺序不能换

① 防负 dt（负值会让 τ 倒退，通道曲线跟着倒放）。② `DT_MAX = 1/30 s` 作用的是**墙钟帧时间**，目的是让任何一段沿都至少能被两帧采到（最窄的沿只有 0.05 s）。③ 慢放**在已经钳好的步长上再缩放**：若顺序反过来（先乘 `TIME_SCALE` 再钳 `DT_MAX`），把 `TIME_SCALE` 调到 10 就会被钳回 1/30，实际速度与设定值不符，而且不报错。现在这个顺序下，慢放只会让步长更小、精度更高。

## 钉帧那一行就是全部

`if (tau < TAU_STAR && tau + dt >= TAU_STAR)` 是一个**跨沿判据**：上一帧还在峰值之前、这一帧的步长足以跨过去。命中时把 τ **直接赋成** `TAU_STAR`（不是加 dt、不是夹取），于是本帧渲染出来的 $u_g$ 逐位等于 1，传送就发生在这一帧。

`tau < TAU_STAR` 这个前半条件承担两件事：**不会重复钉**（钉完 τ 恰好等于 `TAU_STAR`，下一帧条件为假，走正常分支；没有它，`tau + dt >= TAU_STAR` 会一直为真，每帧都传送）、**不会死循环**（这条分支里是 `return`，钉帧那一帧时间线一步都没走）。

代价要量化清楚：整条时间线的墙钟耗时落在 $[\text{T\_TOTAL},\ \text{T\_TOTAL}+dt)$ 内，最多多一帧。60 fps 下是 1.7%，30 fps 下 3.33%。这就是 P7 那条"量化上界"断言的来处（早先按"误差小于 1%"写过，那个指标达不到）。

为什么不能用"解析求峰值"代替钉帧：峰值时刻可以解析算出来，但**传送必须发生在峰值真的被渲染出来的那一帧**。若只在数学上知道峰值在哪、而那一帧画面上的 $u_g$ 是 0.842，背景的视差跳变就会露出来。钉帧钉的不是"τ 的值"，是"必须有一帧把 1 画出来"。

# 第 5 段 · 溶解前沿

```cpp
inline constexpr float NOISE_W = 0.25f;
inline constexpr float FRONT_GEO_START = TAU_STAR - 0.12f;
inline constexpr float FRONT_RETREAT = 0.8f * T_APPEAR;
inline constexpr float FRONT_LO   = -0.5f * NOISE_W;          // -0.125
inline constexpr float FRONT_HI   = 1.0f + 0.5f * NOISE_W;    //  1.125
inline constexpr float FRONT_LEAD = 0.06f;

inline float frontRamp(float tau, float start)
{
    if (tau <= start)       return 0.0f;
    if (tau >= TAU_STAR)    return 1.0f;
    return smoothstep01((tau - start) / (TAU_STAR - start));
}

inline float geoFront(float tau)
{
    float r;
    if (tau <= TAU_STAR)        r = frontRamp(tau, FRONT_GEO_START);
    else if (tau <= T_WIRE_END) r = 1.0f;
    else                        r = 1.0f - smoothstep01((tau - T_WIRE_END) / FRONT_RETREAT);

    return (FRONT_LO - FRONT_LEAD) + (FRONT_HI - FRONT_LO + FRONT_LEAD) * r;
}

inline float matFront(float tau) { return geoFront(tau) + FRONT_LEAD; }
```

## 两个坐标：进度 $r$ 与位置

$r$ 是**进度**（0 到 1 的无量纲小数），函数返回的是**位置**（轴向坐标 $g$ 上的一个值），两者之间是一次线性映射

$$\text{front}(r)=(\text{FRONT\_LO}-\text{FRONT\_LEAD})+(\text{FRONT\_HI}-\text{FRONT\_LO}+\text{FRONT\_LEAD})\,r$$

空间上为什么要 `g`：着色器要把这个返回值直接和 $g_t$ 比大小，所以它必须是 $g$ 的同类量（同单位、同原点）。时间上为什么用 $r$：归一化后 σ 的端点性质直接可用。$\ell=\text{FRONT\_LEAD}$ 同时出现在映射的两个端点上，就是这两套坐标之间唯一的耦合。

## `frontRamp` 的三个分支

在 $[\text{start},\text{TAU\_STAR}]$ 上把时间归一化后过 $s$：起点前返回 0、τ\* 之后**精确**返回 1、中间是 C1 的上升，所以侵蚀速率不会突然起跳。注释里那句"调用方须保证 $\text{start}<\text{TAU\_STAR}$"是硬要求：分母一旦小于等于 0，除零或负斜率会让整段退化。现在 `FRONT_GEO_START = TAU_STAR - 0.12` 由构造满足。

## 端点为什么要超出取值范围

噪声后的轴向坐标范围是 $g_t\in[-w/2,\ 1+w/2]=[-0.125,\ 1.125]$。前沿的两个端点故意落在这个范围**外面**：

- $r=0$ 时 $\text{front}=\text{FRONT\_LO}-\text{FRONT\_LEAD}=-0.185$，比下界还低 0.06。着色器的判据是"$h<\text{front}$ 就丢弃"，于是"存在 $h<-0.185$"恒为假——**静止态一个像素都不会被丢掉**。
- $r=1$ 时 $\text{front}=\text{FRONT\_HI}=1.125$，等于上界，判据变成"除极值点外全部丢弃"，**完成态是干净的**。

这正是"`clamp()` 会把测度零的退化集变成一整片区域"那一课的正面写法：**修法不是加 epsilon 保护，而是让两个取值范围对齐**。当时的错误版本是先把 $g_t$ 夹到 $[0,1]$，负半程的噪声被压成 $g_t=0$ 的一整片平台，而静止时两条前沿恰好都在 0 附近，$\mathrm{smoothstep}(0,0,g_t)$ 在 $g_t=0$ 处是 $0/0$，于是**静止态**艏部冒出一片青绿。静止态是程序的稳态，最显眼又最不在测试里。

## `matFront = geoFront + FRONT_LEAD`

材质前沿永远比几何前沿多 0.06，是个空间量、不是时间量。它一次性解决两件事：着色器里 $\mathrm{smoothstep}(\text{uFrontGeo},\text{uFrontMat},h)$ 要求 `edge0 < edge1`，间距恒正就使两个边界**永不相等也永不交叉**，不会出现 GLSL 里 `edge0 > edge1` 的未定义行为；顺带删掉了上一版那个越冲常数 `FRONT_OVER`——它的思路是"让几何前沿冲过头"，结果在 τ 接近 τ\* 时两条前沿交叉、边界反转，症状是切口发光突然翻到另一侧。

于是"两级溶解"的顺序是：同一处**先把材质剥掉**（贴图没了、压暗、粗糙度拉满、法线换回几何法线），**几何被丢弃在后**；返程反过来，先长出裸结构，材质再补回来。

## 三段的时间结构

去程 $[\text{FRONT\_GEO\_START},\text{TAU\_STAR}]$ 由 `frontRamp` 把 $r$ 从 0 升到 1。起点落在**隐没段内**，所以"开始被吃掉"与"白化到顶"是重叠的。线框段 $r\equiv 1$，几何整段保持全剥。返程 $r=1-s(\cdot)$ 从 1 退回 0，终点精确落在 $\text{T\_WIRE\_END}+\text{FRONT\_RETREAT}=1.20$，在 `T_TOTAL` 之前（也正好在 $A_{f1}=1.22$ 之前 0.02）。

## 噪声那两句

$g_t=g+\text{NOISE\_W}\cdot(n-0.5)$：

- **要减 0.5**。不减的话噪声均值是 0.5，前沿的平均位置会被整体推偏 $w/2=0.125$（舰长的 12.5%）。
- **不能夹到 $[0,1]$**。理由见上，且不夹之后取值范围天然就是 $[-w/2,1+w/2]$，两条前沿的取值域已经覆盖它，不需要任何保护。
- 噪声入参是 $q=\text{ObjPos}/\text{uObjRadius}$ 再乘频率。先除以半径是为了**让频率与模型尺寸无关**：物体空间坐标比世界大 2000 倍，直接拿 `ObjPos` 乘频率会得到逐像素噪点而不是连续的侵蚀面。

# 第 6 段 · 预备动作与拉伸包络

```cpp
inline float anticipation(float tau)
{
    if (tau <= 0.0f) return 0.0f;
    if (tau <= T_CHARGE) return quintic01(tau / T_CHARGE);
    if (tau <= TAU_STAR)return 1.0f - quintic01((tau - T_CHARGE) / T_VANISH);
    return 0.0f;
}
```

`anticipation` 返回的是**归一化退距**（取值 $[0,1]$）：蓄能期内从 0 升到 1，随后在隐没段内退回 0，并在 τ\* 处**精确**回到 0。调用方把它乘上 $\kappa\,D$（`KAPPA_BACK * WARP_DISTANCE`，即 1.5 世界单位）并沿 $-\hat f$ 施加到**模型矩阵**上。

三个要点：

- **绝不能施加到 `ship.position`**。它是纯视觉偏移；一旦进入物理量，传送的位移不变式（P4：舰体与相机平移同一个向量）就破了，而且这个错误会以"影子滑开、相机相对抖"的形式出现在离肇事点很远的地方。
- 为什么用 $\varphi$ 而不是 $s$：这是**位移**，二阶导是加速度。用 $s$ 的话，起步瞬间加速度从 0 跳到 6，观感就是"起步一顿"。
- 为什么必须在 τ\* 精确归零：那一帧是命题 2 约束的帧，任何额外的位移都会让"舰体与相机同步平移"这句话不成立。

时间上它是一条"先退后还"的曲线：蓄能期我缓缓向后退一点（预备动作），隐没段把这 1.5 单位还回去，起跳前归零。两段都用 $\varphi$，接缝处一阶二阶导都是 0，所以整条曲线 C2。

```cpp
inline constexpr float STRETCH_RISE = TAU_STAR - 0.15f;   // 拉伸起点（隐没段之内）
inline constexpr float STRETCH_HOLD_END = T_WIRE_END;     // 1.00
inline constexpr float STRETCH_FALL = T_APPEAR;           // 0.25

inline float stretchAmount(float tau)
{
    if (tau <= STRETCH_RISE)     return 0.0f;
    if (tau <= TAU_STAR)         return quintic01((tau - STRETCH_RISE) / (TAU_STAR - STRETCH_RISE));
    if (tau <= STRETCH_HOLD_END) return 1.0f;
    if (tau >= STRETCH_HOLD_END + STRETCH_FALL) return 0.0f;
    return 1.0f - quintic01((tau - STRETCH_HOLD_END) / STRETCH_FALL);
}

inline float stretchFactor(float amount)
{
    return 1.0f + E_STRETCH * amount;
}
```

## 为什么不让它跟着 `u_v` 走

第一版是把 `stretchFactor` 直接接到 `u_v` 上的。问题是 `u_v` 是**隐没段的白化通道**：它在隐没段到顶、在抵达段已经是 0，于是"抵达时拉长着出现、再缩回原比例"这个动作根本不会发生。**一个量只能有一个语义**：`u_v` 的语义是"白化强度"，不是"形变强度"。所以拉伸拿到了自己的包络。

## 为什么峰值必须"保持"

第二版把峰值放在 τ\* 之后就立刻回落，结果看不出来：τ\* 那一帧舰体已经被剥光，之后到 `T_WIRE_END` 为止场上只剩线框，收缩若发生在这一段就等于没发生。代进数值验算一下：回落段长 0.55 s 时，实体化开始那一刻的拉伸量只剩 $1+0.35\,(1-\varphi(0.35/0.55))\approx1.09$，也就是说真正有材质的时候拉伸基本没了。改成"升到 τ\*、保持整个线框段、与实体化同期收回"之后，看得见的那一段才是完整的一次"拉长到还原"。

现在这条包络有四段：起于 `TAU_STAR - 0.15`（落在隐没段内）升到 1、在 $[\text{TAU\_STAR},\ \text{T\_WIRE\_END}]$ 保持、在 $[\text{T\_WIRE\_END},\ \text{T\_TOTAL}]$ 收回。**终点由构造精确**：$\text{T\_WIRE\_END}+\text{STRETCH\_FALL}=\text{T\_TOTAL}$，所以时间线结束那一帧拉伸恰好归 1，不会跳。

## 缓动与映射为什么分开

`stretchAmount` 只出 $[0,1]$ 的"量"，`stretchFactor` 做 $1+E\,a$ 的线性映射。这样想单独调幅度只改 `E_STRETCH`、想调节奏只改时间常量，两件事不互相污染。整条包络在三处接缝都 C2：常值段导数为零，$\varphi$ 两端一阶二阶导为零。

## `cpp` 侧：缩放的不动点决定"哪一端先动"

```cpp
const float stretch = warp::stretchFactor(warp::stretchAmount(gWarp.tau));
if (stretch > 1.0f)
{
    const float yAnchor = (gWarp.tau <= warp::TAU_STAR) ? shipAxisMaxY : shipAxisMinY;
    shipModel = shipModel
        * glm::translate(glm::mat4(1.0f), glm::vec3(0.0f, yAnchor, 0.0f))
        * glm::scale(glm::mat4(1.0f), glm::vec3(1.0f, stretch, 1.0f))
        * glm::translate(glm::mat4(1.0f), glm::vec3(0.0f, -yAnchor, 0.0f));
}
```

模型局部 **+Y 指向艉**（`Forward() = heading * (0,-1,0)`，而 `GetModelMatrix` 是 $T\,R\,S$），所以：

- 锚在 `shipAxisMaxY`（艉）时艉钉死、艏被往外拉，读作**去程"头先被拉长"**；
- 锚在 `shipAxisMinY`（艏）时艏就停在它的最终位置上、只有艉收回，读作**抵达"头先还原"**。

`glm::scale` 绕物体原点缩放，不动点在原点，所以要让不动点落在 $a$ 上必须两边各夹一层平移：$T(a)\,S\,T(-a)$ 对任意点 $p$ 给出 $a+s(p-a)$，$p=a$ 处不动。

**单位必须搞清**：整条链是 $T(\text{pos})\,R\,S(0.0005)\cdot[T(a)\,S_y\,T(-a)]$。夹心是**后乘**，所以它作用在物体空间，$a$ 必须是物体空间的 $\pm53668$（模型顶点坐标），而不是世界空间的 $\pm26.8$。写错单位或顺序的症状很单一：**折跃时舰体整体瞬移一大截**。

**为什么锚点切换放在 τ\* 看不见**：那一帧 `geoFront = FRONT_HI`，舰体被完全剥除；电流外壳通道在 0.62 已经归零；而线框与蓝图用的是**不含拉伸**的 `shipWireModel`，与锚点无关。三种绘制在那一帧都与锚点无关，所以切换不可见，不需要任何过渡。

**为什么拉伸只进模型矩阵**：阴影 pass 共用同一个 `shipModel`，所以影子跟着形变走（分开算会让"舰体在拉长、影子却没拉长"）；而一旦写进 `ship.position`，就会破坏传送的位移不变式。

## 7.1 FOV 冲击（推镜）

```cpp
inline constexpr float FOV_KICK    = 3.5f;                  // Φ，单位是度
inline constexpr float SHAKE_AMT   = 0.30f;                 // 世界单位
inline constexpr float KICK_START  = TAU_STAR - 0.07f;      // FOV 冲击起点
inline constexpr float KICK_END    = TAU_STAR + 0.30f;      // FOV 冲击归零点
inline constexpr float SHAKE_START = TAU_STAR - 0.02f;      // 抖动起点（在闪现上升段之内）
inline constexpr float SHAKE_DECAY = 0.15f;                 // 抖动衰减时长

inline float fovKick(float tau)
{
    if (tau <= KICK_START) return 0.0f;
    if (tau <= TAU_STAR)   return quintic01((tau - KICK_START) / (TAU_STAR - KICK_START));
    if (tau >= KICK_END)   return 0.0f;
    return 1.0f - quintic01((tau - TAU_STAR) / (KICK_END - TAU_STAR));
}
```

- 它是**长包络**：起于 τ\* − 0.07、峰在 τ\*、归零于 τ\* + 0.30，总跨度 0.37 s，读作一次推镜。
- 两段都用 φ：FOV 的变化被眼睛读成**运动**（镜头在推），不是明暗，所以加速度必须连续。φ 两端一阶二阶导都为零，整条曲线 C2，起止都不会"顿"。
- 起点与归零点都锚在 τ\* 上，于是产生一条结构性约束 `KICK_END ≤ T_WIRE_END`，退化成 `T_WIRE ≥ 0.30`（现在是 0.35，余量 0.05）。
- 幅度常量与时间常量分开：`FOV_KICK = 3.5` 是**度**，在投影矩阵那一处被乘进 `camera.Fov`。

**为什么峰值必须落在 τ\***。真正的原因不是"躲开那一帧"，而是**峰值处导数为零**：两条包络在 τ\* 的左右导数都是 0（φ'(0) = φ'(1) = 0），所以传送那一帧它们对相机偏移与 FOV 的**帧间增量**贡献恰好为 0，于是命题 2 要求的"舰体与相机平移同一个向量"精确成立。若峰值错开 τ\*，那一帧相机就会多出一个非零增量，舰体的屏幕姿态会跟着挪一下。

代码里那段注释（"两者都只在传送之后才起来"）与实际不符：`KICK_START = TAU_STAR - 0.07` 比 τ\* 早 0.07 s，抖动也早 0.02 s。它的后半句是对的（在 `T_WIRE_END` 之前归零，不污染后续相机阻尼——跟随相机每帧朝目标 mix，残留偏移会一直被带着走），前半句应当换成上面这个理由。

## 7.2 抖动（短促一顶）

```cpp
inline float shakeEnvelope(float tau)
{
    if (tau <= SHAKE_START) return 0.0f;
    if (tau <= TAU_STAR)    return quintic01((tau - SHAKE_START) / (TAU_STAR - SHAKE_START));
    if (tau >= TAU_STAR + SHAKE_DECAY) return 0.0f;
    return 1.0f - quintic01((tau - TAU_STAR) / SHAKE_DECAY);
}
```

- **短包络**：升起只用 0.02 s（几乎与闪现上升段同时），之后在 `SHAKE_DECAY = 0.15` s 内落回 0，总跨度 0.17 s。与 FOV 的 0.37 s 形成"顶一下"与"推一程"的对比。
- **刻意不复用 `fovKick`**：复用的话抖动会拖到 0.37 s，读起来不是短促一顶，而是缓慢漂移。
- 幅度 `SHAKE_AMT = 0.30` 世界单位。舰体全长 53.7 世界单位，所以峰值偏移约 0.6% 舰长——小到只是"肩膀被撞了一下"，大到看得出来，是实调值。
- 它与 FOV 有一个本质区别：FOV 只改投影，**抖动真的移动相机**（在 `view` 矩阵上先加偏移、画完再减回去）。所以"峰值对齐 τ\*"这条理由对它更硬：峰值不在 τ\* 的话，传送那一帧相机会多出一个非零位移增量，命题 2 就不再精确成立。

## 7.3 骨架的生长位置与强度

```cpp
inline constexpr float WIRE_GROW_TIME = T_CHARGE;   // 自艏画到艉所用的时间

inline float wireGrow(float tau)
{
    if (tau <= 0.0f)           return 0.0f;
    if (tau >= WIRE_GROW_TIME) return 1.0f;
    return smoothstep01(tau / WIRE_GROW_TIME);   // 平滑版；等速版为 tau / WIRE_GROW_TIME
}

inline float wireAlpha(float tau)
{
    if (tau <= 0.0f) return 0.0f;
    return 1.0f - smoothstep01((tau - W_F0) / (W_F1 - W_F0));
}
```

这一小节是整个折跃里**返工次数最多**的地方，值得把每一次返工的理由都记下来。

**（1）位置与强度必须分成两件事。** 最早的写法直接把 `u_w` 当生长位置。`u_w` 是梯形，在 `[0.95, 1.08]` 上会落下，于是线框长到艉之后会**从艉向艏缩回去**：位置一旦用了会回落的量，就必然出现倒放。分开之后，位置是一根单调不减的曲线，强度是另一条包络。

**（2）生长曲线为什么锚在按键而不是 τ\*。** 第二版让它在 τ\* 起步、0.20 s 画满。加上"目的地蓝图"之后这条不再成立：蓝图在蓄能期就把骨架画在落点了，传送后那份线框与它是**同一世界位置上的同一副骨架**；前沿若在闪白之后还没到头，它会把蓝图画了一半的那截"接手"过去，读起来是蓝图白画。所以前沿必须**在传送之前画满**，传送之后恒为 1。

**（3）为什么把 `WIRE_GROW_TIME` 挂到 `T_CHARGE`。** 挂绝对秒数时，蓄能段一拉长，画的过程就只占前面一小截，后面全是"完整骨架在等"。挂 `T_CHARGE` 之后语义固定为"铺满整个蓄能段"，而且蓄能段怎么改，这条曲线的形状不变（同一相对位置上画到的比例完全一样）。

**（4）强度为什么不能继续用 `u_w`。** `u_w` 的上升段 `[0.62, 0.70]` 是为"线框随传送出现"设计的：那时落点还没有任何东西，需要淡入。现在骨架自蓄能期就在场，再淡入一次就会在 τ\* 前后掉一次亮度——`u_w` 在 τ\* 处只有 0.316，而蓝图那一刻是 1.00，交接处于是变成 1.00 掉到 0.32、再花 0.05 s 回到 1.00，那 0.05 s 就是一次可见的掉亮。**模式 1/2 没有全屏白遮着，看起来就是闪断**。所以强度只保留 `u_w` 的下降沿，并且按 `W_F0` / `W_F1` 引用，淡出时机仍然只在通道表里改一处。

**（5）三段的完整时序。** `0` 到 `T_CHARGE`：骨架在落点自艏画满，强度恒为 1；`T_CHARGE` 到 `W_F0`（0.95）：满亮保持，其中 τ\* 那一帧由"蓝图"换成"舰体位置上的线框"，位置、形状、亮度三者相同，所以读成一次；`0.95` 到 `1.08`：平滑淡出，材质重建接手。

**（6）一个容易漏的连带关系。** `u_w` 现在只剩"投影门限"这一个消费者（`solid = clamp01(1 - u_v - u_w)`），线框的明暗改由 `wireAlpha` 负责。所以"线框不再是 `u_w` 画的"并不影响阴影逻辑：舰体仍在 `[0.62, 0.70]` 之间停止投影，时机与原来一致。

# 第 8 段 · 瞬时重定位与定步长插值

## 8.1 先把三套坐标约定钉死

```cpp
glm::vec3 Forward() const { return heading * glm::vec3(0.0f, -1.0f, 0.0f); }
glm::vec3 Up()      const { return heading * glm::vec3(0.0f,  0.0f, -1.0f); }

glm::mat4 GetModelMatrix(float a) const
{
    glm::mat4 m = glm::mat4(1.0f);
    m = glm::translate(m, RenderPosition(a));
    m = m * glm::mat4_cast(RenderHeading(a));
    m = glm::scale(m, glm::vec3(0.0005f));
    return m;
}
```

- 机头在模型局部 **−Y**（`Forward` 取的就是 `heading * (0,-1,0)`），上方在局部 **−Z**。由此局部 **+Y 指向艉**。
- 第 5 段的溶解轴向 `g = 0 在艏`、第 6 段的拉伸锚点"去程锚艉、抵达锚艏"，全部建立在这两条上。**这两条一旦理解反了，所有方向性改动都会整体反向。**
- `GetModelMatrix` 是 $T \cdot R \cdot S$：最后那个 `0.0005` 是模型的统一缩放，所以**物体空间坐标比世界大 2000 倍**（战列巡航舰的 Y 向半长是 53668 物体单位，折算 26.8 世界单位，全长 53.7）。凡是"物体空间量"的 uniform（`uAxisMinY/MaxY`、拉伸锚点）都必须用 53668 那一套单位，写错量级的症状是画面整体崩掉而不是"稍微偏一点"。

## 8.2 `WarpTo`：为什么写两个字段而不是一个

```cpp
// 同时写 position 与 prevPosition。当 prevPosition == position 时，
// 渲染插值  prev + a * (cur - prev)  对任意 a ∈ [0,1) 都退化为精确值，
// 于是传送不可能被涂抹。只写 position 的后果：偏差为 (1-a)*D，
// 上确界正好是 D = 100 单位，屏幕上表现为舰体在一帧内被拉过整个折跃距离。
void WarpTo(const glm::vec3& target)
{
    position = target;
    prevPosition = target;
    prevHeading = heading;
}
```

渲染用的位置是插值出来的：

$$P_{\text{render}}(a) = (1-a)\,P_{\text{prev}} + a\,P_{\text{cur}},\qquad a\in[0,1)$$

**只写 `position` 会怎样**：设传送前位置为 $P$、位移为 $D$，则 $P_{\text{prev}}=P$、$P_{\text{cur}}=P+D$，代进上式得

$$P_{\text{render}}(a) = P + a\,D$$

舰体被渲染在从 $P$ 到 $P+D$ 之间的某处，偏差是

$$\big(P+D\big) - \big(P+a\,D\big) = (1-a)\,D$$

在 $a\in[0,1)$ 上取上确界（$a\to 1^-$）恰为 $|D| = 100$ 世界单位。也就是说：**传送那一帧舰体会被拉过整个折跃距离**，而不是"瞬移"。

**同时写 `prevPosition` 之后**：$P_{\text{prev}} = P_{\text{cur}} = P'$，插值退化成

$$P_{\text{render}}(a) = (1-a)P' + aP' = P'$$

与 $a$ 无关，所以无论这一帧跑了几个物理步、`alpha` 是多少，取到的都是落点本身。严格说 `glm::mix` 是 `x*(1-a) + y*a`，$x=y$ 时两项相消仍会经过浮点舍入，所以是"最多差 1 ulp"而不是逐位相等；但涂抹量从这个量级上讲已经从"100 世界单位"降到"1 ulp"。（P5 断言里那句 `prevPosition == position (bitwise)` 说的是**字段**的逐位相等，那是直接赋值，成立；插值出来的值本身是用容差比的。）

**为什么连 `prevHeading` 一起同步**。折跃本身不改变朝向，所以这一行在当下是"多余的"。留着它是为了让 `WarpTo` 成为一个**无条件不可插值**的传送入口：`RenderHeading(a) = slerp(prevHeading, heading, a)`，万一以后有人让折跃顺带调整姿态，忘了同步 `prevHeading` 就会让舰体在一帧内从旧姿态"旋"到新姿态——那是同一个 bug 的旋转版本。代价是一次赋值，收益是这条不变量不依赖"折跃不改朝向"这个当前事实。

## 8.3 `AdvanceFixed`：定步长、渲染插值、以及两个必须记住的细节

```cpp
static constexpr float FIXED_DT   = 1.0f / 120.0f;
static constexpr float MAX_ACCUM  = 0.25f;

int AdvanceFixed(float& accum, float frameDt, float& alpha)
{
    accum += frameDt;
    if (accum > MAX_ACCUM)
    {
        accum = MAX_ACCUM;
    }
    int steps = 0;
    while (accum >= FIXED_DT)
    {
        FixedUpdate(FIXED_DT);
        accum -= FIXED_DT;
        ++steps;
    }
    alpha = accum / FIXED_DT;
    return steps;
}
```

**① `accum` 必须是引用 `float&`。** 调用方（主循环）持有它并跨帧保留。按值传参的话，每帧结束时剩下的那个余数会被丢掉，下一帧又从 0 开始累加，于是步数在 1 步与 2 步之间交替，画面上表现为舰体"一卡一卡"。这个 bug 真的发生过，而且从代码上看不出来——函数体完全正确，错的是签名。

**② 循环边界必须是 `>=` 而不是 `>`。** 用 `>` 的话，累加器里会长期滞留一个整步，`alpha` 的分母也随之失真，步数同样会在两个值之间摆动。

**③ `alpha ∈ [0,1)` 是推导出来的，不是假设。** 循环退出的条件是 `accum < FIXED_DT`，所以 `alpha = accum / FIXED_DT < 1`。正因为如此，$[P_{\text{prev}}, P_{\text{cur}}]$ 恰好夹住**一个** `FIXED_DT`，插值在两端都不外推。

**④ `MAX_ACCUM = 0.25` 是"卡顿钳制"。** 一次长卡顿（换窗口、断点、加载）会让 `frameDt` 变成几秒，不钳的话这一帧要补几百个物理步，画面会直接冻住更久（追帧雪崩）。钳到 0.25 s 之后，最多补 30 步（$0.25 / (1/120) = 30$），代价是那段时间的物理"少走了"，但舰体的运动本身是解析积分，少走几步只是位置略微落后，不会炸。T2 断言守的就是这条（卡顿后 29 到 30 步）。

**⑤ 返回值 `steps`** 给自测与运行期探针用（T1 帧切分、可选的每秒步频汇总），绘制路径不用它。

## 8.4 `FixedUpdate`：先快照再积分

```cpp
void FixedUpdate(float dt)
{
    prevPosition = position;
    prevHeading  = heading;
    Update(dt);
}
```

顺序不能反。插值有效的全部依据是"$P_{\text{prev}}$ 是这一步**之前**的位置"；写成先 `Update(dt)` 再快照，快照下来的就是积完之后的位置，`[prev, cur]` 退化成零区间，插值静默失效——画面不会报错，只是回到"渲染帧与物理帧对齐"的最粗状态，也就是掉帧时抖动。这条同样是自测守的（T4 步进器不变式）。

**传送为什么不在固定步里**。`WarpTo` 由主循环在**这一帧的物理步进之后**调用，属于"每帧事件"而不是"物理步事件"。它写的是同一帧渲染要用的那两个字段，所以插值因子再大也取到落点；反过来，如果把它塞进 `FixedUpdate`，一次 `AdvanceFixed` 跑两步时就会传送两次（第二次把已经到位的舰体再推 100 单位），位移直接翻倍。这条与第 4 段"钉帧只允许发生在跨沿的那一帧"是同一个约束的两个侧面。

# 第 9 段 · 折跃自测（P1–P7）

## 9.1 约定：header-only + 自 gate

```cpp
#pragma once
#ifdef DEBUG_PHYS
    // ... 全部真实实现 ...
    namespace warp_test { inline void Run() { /* P1..P7 */ } }
#else   // !DEBUG_PHYS —— 非 Debug 配置下不产生任何代码
    namespace warp_test { inline void Run() {} }
#endif
```

- 真实实现包在 `#ifdef DEBUG_PHYS` 内，`#else` 提供一个空的 `inline void Run()`。于是**调用点不需要任何 `#ifdef`**（`main` 第一行直接写 `warp_test::Run();`），新增自测也**不用动 vcxproj 的预处理器定义**。`DEBUG_PHYS` 只出现在 `Debug|x64` 那一组里。
- **这套约定的固有代价**：切到不含该宏的配置时，自测会**静默变成空函数**——不报错、不打印、不失败。唯一的判据是控制台有没有 `===== warp self test (P1..P7) =====` 那一行。所以"我跑过了，全绿"这句话必须带上"而且我看见 banner 了"，否则可能根本没跑。
- `WARP_TEST_HARD_FAIL` 默认 0：失败只打印。置 1 则失败当场 `assert(false)`。默认不置 1 是有意的——让自测每次启动都能跑完、列出**全部**失败项，而不是在第一处就停下。
- 两个断言函数：`Check(ok, name, got, want, tol)` 会把实测值与期望值打成 `%.9g`（够看清 float 的每一位），`CheckTrue(ok, name)` 用于"存在性、唯一性"这类没有数值可比的场合。`gFail` 是命名空间内的 `inline int`，`Run()` 开头清零、结尾汇总。

**为什么这套自测值得存在**：折跃里出过四个错误——`advance` 漏写 `= true`（传送根本没发生）、`flash()` 漏 `return`（未定义行为）、`frontRamp` 漏 `return`、着色器 `filaments()` 两处转录错——**没有一个能用眼睛在运行时抓出来**，全是断言抓的。眼检与目视运行对这类转写错误基本无效，这是这个工程反复付过学费的一条。

## 9.2 P1 —— 命题 1：可见性不中断

```cpp
const float step = 0.001f;
for (float t = step; t < 1.22f; t += step)
{
    const warp::Channels c = warp::sample(t);
    float m = c.c;
    if (c.v > m) m = c.v;
    if (c.g > m) m = c.g;
    if (c.w > m) m = c.w;
    if (c.a > m) m = c.a;
    if (m < worst) { worst = m; worstTau = t; }
}
Check(worst > 0.0f, "P1  max(u_c,u_v,u_g,u_w,u_a) > 0 on (0,1.22)", ...);
```

- 断言的是：在开区间 $(0,1.22)$ 上以 0.001 s 采样，$\max(u_c,u_v,u_g,u_w,u_a)$ **从不为 0**。也就是说每一帧都至少有一个效果在起作用，不会出现"什么都不画、画面空一拍"。
- 为什么是**开**区间：$\tau=0$ 与 $\tau>1.22$ 处五个通道本就同时为零，那两处走的是常规不透明舰体路径、还没有发生任何跳变，不构成缺陷（计划书 注 2）。若把端点算进来，这条断言会永远失败，而失败的原因毫无意义。
- 为什么上界取 1.22 而不是 `T_TOTAL`：所有通道在 1.22 之前归零，最后 0.03 s 是留给钉帧的余量；用 1.22 才是"效果确实还在"的那一段。
- 采样步长 0.001 s 比现有最窄的沿（0.05 s）细 50 倍，所以不会漏。**它的局限也在这里**：这是采样检查而不是解析检查，将来若做出比 0.001 s 还窄的沿，它会漏过去。
- 失败时会额外打印"最暗的一帧出现在 tau = ..."，这是诊断友好型写法：断言告诉你坏了，附带信息告诉你坏在哪。

## 9.3 P2 —— 通道表的峰值条件

```cpp
const Row rows[4] =
{
    { "u_c", warp::C_R0, warp::C_R1, warp::C_F0, warp::C_F1 },
    ...
};
for (int i = 0; i < 4; ++i)
{
    CheckTrue(rows[i].r1 <= rows[i].f0, buf);              // 硬性约束
    const float mid  = 0.5f * (rows[i].r1 + rows[i].f0);   // 平台中点
    const float peak = warp::trap(mid, rows[i].r0, rows[i].r1, rows[i].f0, rows[i].f1);
    Check(std::fabs(peak - 1.0f) < 1e-6f, buf, peak, 1.0f, 1e-6f);
}
```

- 每条通道断言两件事：$r_1\le f_0$ 成立；平台中点处的 $trap$ 值等于 1。
- 这两条守的是同一个失效模式：某一行写成 $r_1>f_0$ 时，两段斜坡在 $(f_0,r_1)$ 上相乘，峰值达不到 1，**而且不报任何错**，你只会看到那一段莫名其妙偏暗。第一条断言定位到"哪一行违反了约束"，第二条断言定位到"峰值确实不是 1"。
- 平台中点是最稳的采样点：中点处 $up$ 的参数 $\ge 1$、$down$ 的参数 $\le 0$，$s$ 自带 clamp，所以两条因子**精确**饱和，峰值是精确的 1；那个 `1e-6` 容差只是保险。
- **关键性质**：`rows` 里读的是 `warp::C_R0` 这些常量本身，所以**你改通道表，这条断言自动跟着检查新数值**。这就是操作表里"改完必查第一条"有机器兜底的原因。
- 局限：它只检查"峰值是 1"，不检查**什么时候**到峰值、也不检查通道之间的搭接是否还有重叠。

## 9.4 P3 —— 命题 3：任意帧率下峰值必被采到

```cpp
const float dts[3] = { 1.0f/30.0f, 1.0f/60.0f, 1.0f/144.0f };
for (int i = 0; i < 3; ++i)
{
    float tau = 0.0f;
    int peakFrames = 0, teleportFrames = 0;
    bool teleportOnPeak = false;
    for (int f = 0; f < 100000; ++f)
    {
        const warp::Step s = warp::advance(tau, dts[i]);
        const float g = warp::sample(tau).g;
        if (g >= 1.0f) { ++peakFrames; if (s.teleport) teleportOnPeak = true; }
        if (s.teleport) ++teleportFrames;
        if (s.finished) break;
    }
    // 三条：peakFrames >= 1；teleportFrames == 1；teleportOnPeak
}
```

- 三种帧率各跑一遍完整时间线，断言三件事：**存在至少一帧 $u_g$ 达到 1**、**传送恰好发生一次**、**传送就发生在峰值那一帧**。
- 为什么用 `g >= 1.0f` 而不是 `== 1.0f`：`flash` 是 `clamp01` 出来的，最大值精确为 1，所以两者等价；写成 `>=` 更清楚地表达"到达过峰值"这个语义。
- 30 fps 这一档是关键：闪现上升段只有 0.05 s，而一帧走 1/30 s，不钉帧就会整帧跨过峰值。144 fps 那一档则覆盖高刷屏。60 fps 是常态。三档一起跑，等于把"帧率无关"这件事同时从两个方向夹住。
- **这条断言是"漏写 `= true`"那个 bug 的守门人**：传送标志没置起来时 `teleportFrames` 是 0、`teleportOnPeak` 是 false，两条一起红。（当时 P3 与 P7 同时报警，是它们把那个错误揪出来的。）
- 循环上界 100000 帧是防死循环的保险；正常在 `finished` 处退出。

## 9.5 P4 —— 命题 2：位移不变式

```cpp
const glm::vec3 P(12.5f, -3.25f, 88.0f);
const glm::vec3 K(-40.0f, 10.0f, 200.0f);
const glm::vec3 d(31.0f, -17.5f, -62.75f);

const float before = glm::length(K - P);
const float after  = glm::length((K + d) - (P + d));
Check(std::fabs(after - before) < 1e-5f, "P4  |(K+d)-(P+d)| == |K-P|", ...);
```

- 它验证的是"舰体与相机同时加同一个 $d$，两者的相对位姿不变"，即 $\lVert(K+d)-(P+d)\rVert = \lVert K-P\rVert$。实数上精确成立，浮点上因为两次加法的舍入会差一点点，所以给 $10^{-5}$ 的容差。
- **它的局限必须说清**：这条断言只证明了**算术恒等式**，它**无法证明 cpp 里真的对舰体与相机用了同一个 `delta`**。后者没有断言覆盖，只能靠人工核对（第 10 段会过一遍那两行）。这是"测试覆盖的是命题，不是实现"的典型例子，别把它当成实现已经守住了。

## 9.6 P5 —— 传送不可被插值涂抹

```cpp
Spaceship s;
const glm::vec3 target(5.5f, -2.25f, 70.125f);
s.WarpTo(target);

const bool posOk = (s.position.x == target.x) && (s.position.y == target.y) && (s.position.z == target.z);
CheckTrue(posOk, "P5  WarpTo writes position");

const bool prevOk = (s.prevPosition.x == s.position.x) && ... ;
CheckTrue(prevOk, "P5  prevPosition == position (bitwise)");

const float alphas[3] = { 0.0f, 0.5f, 0.999f };
for (...) Check(err < 1e-4f, "P5  RenderPosition(a=...) == P", ...);
```

- 它是唯一一条**碰真实类**的断言：直接构造一个 `Spaceship`（不走 GL），调 `WarpTo`，再检查三件事——`position` 等于目标、`prevPosition` 与 `position` 逐位相等、以及三个 `alpha`（含 0.999 这个接近 1 的边界）处的 `RenderPosition` 都还在 $10^{-4}$ 以内。
- **两半句为什么精度要求不同**，代码注释里写清了：前半句是直接赋值，可以逐位比；后半句是 `glm::mix(p, p, a)`，它先算 $p(1-a)$ 与 $pa$ 再相加，两次乘法各自舍入后不保证还原 $p$，所以必须给容差。这条正是"曾经把 `bitwise` 说过头"之后改回来的写法——**断言里每句话的强度都要与它真正验证的东西匹配**。
- 三个 alpha 的选取：0 与 0.999 是区间的两端（0.999 比 1 更接近真实的上确界），0.5 是中间。若有人把 `WarpTo` 改成只写 `position`，`prevPosition == position` 会立刻红，同时三个插值检查的误差会跳到 $|(1-a)D|$ 量级。

## 9.7 P6 —— 两端导数条件（C1 与 C2 的判别式）

```cpp
const float h = 1e-3f;
const float s0 = (warp::smoothstep01(h) - warp::smoothstep01(0.0f)) / h;   // 近似 s'(0)
const float q0 = (warp::quintic01(h)   - warp::quintic01(0.0f))   / h;   // 近似 φ'(0)
... // 四个一阶（两端各两个）都断言 |·| < 1e-2

const float s2 = (warp::smoothstep01(2h) - 2*warp::smoothstep01(h) + smoothstep01(0)) / (h*h);
const float q2 = (warp::quintic01(2h)   - 2*warp::quintic01(h)   + quintic01(0))   / (h*h);
Check(std::fabs(s2 - 6.0f) < 1e-1f, "P6  sigma''(0) ~ 6  => not C2", ...);
Check(std::fabs(q2)      < 2e-1f, "P6  phi''(0)   ~ 0  => is C2", ...);
```

- 用**单侧差分**而不是解析式，才能查出实现被写错（例如 $\varphi$ 的系数抄错一位）。拿解析公式跟自身比等于什么都没验。
- 阈值不是随手取的，是按单侧差分的**余项量级**定的：
  - 一阶前向差分 $\big(f(h)-f(0)\big)/h$ 的余项是 $O(h)$。代 $s$ 得 $3h$、代 $\varphi$ 得 $10h^2-15h^3+6h^4$，$h=10^{-3}$ 时都在 $10^{-5}$ 量级，取 $10^{-2}$ 的阈值留了三个数量级。
  - 二阶前向差分 $\big(f(2h)-2f(h)+f(0)\big)/h^2$ 对 $\sigma$ 给出 $6-12h=5.988$、对 $\varphi$ 给出 $60h-210h^2\approx 0.0598$。所以阈值一个取 $10^{-1}$（判别 6）、一个取 $2\times10^{-1}$（判别 0）。
- 最后那一对才是**判别式**：$\sigma''(0)=6\neq 0$ 说明 $\sigma$ 不是 C2，$\varphi''(0)=0$ 说明 $\varphi$ 是 C2。第 2 段讲的"运动用 $\varphi$、明暗用 $\sigma$"这条分配原则，在自测里就落在这一对上。
- 局限：只查了 $x=0$ 与 $x=1$ 两端，没有查中间；$\varphi$ 的单调性、$s$ 与 $\varphi$ 在 0.5 处都等于 0.5 这些性质也没有断言（那些更多是定义性事实）。

## 9.8 P7 —— 实际用时的量化上界

```cpp
float tau = 0.0f, wall = 0.0f;
int pinFrames = 0;
for (int f = 0; f < 100000; ++f)
{
    const warp::Step s = warp::advance(tau, dt);
    wall += dt;
    if (s.teleport) ++pinFrames;
    if (s.finished) break;
}
CheckTrue(wall >= warp::T_TOTAL && wall < warp::T_TOTAL + 2.0f * dt, buf);
CheckTrue(pinFrames == 1, buf);
```

- 断言实际墙钟耗时落在 $[\text{T\_TOTAL},\ \text{T\_TOTAL}+2\,dt)$ 内，并且钉帧恰好发生一次。
- **偏差只有两个来源**：逐帧采样把 $\tau$ 取整到帧边界，最多多花一帧；钉住那一帧 $\tau$ 没走，等于再多花一帧。所以上界是 $2\,dt$，不是 $dt$。30 fps 时这等于 $6.7\%$ 的绝对量、相对 $\text{T\_TOTAL}=1.25$ 是 $5.3\%$ —— 这是**逐帧采样的固有代价，不是缺陷**。
- 这条断言的历史意义：早先版本按"误差小于 1%"写过指标，那个指标达不到（它把钉帧那一帧漏算了），所以断言与文档一起改成现在这个可证的上界。**"指标写不出来就别写"比"写个好看的数"重要**。
- `pinFrames == 1` 是 P3 那三条的第二道锁：即使峰值被采到，若钉帧判据写成 `>` 或漏了 `tau < TAU_STAR` 的前半条件，这里会变成 2 或更多。

## 9.9 覆盖缺口（诚实清单）

自测覆盖的是"时间线数学"，不是全部折跃代码。目前明确没有断言覆盖的有：

1. **溶解前沿的端点语义**：`frontRamp` / `geoFront` / `matFront` 一条都没测。而**唯一一次出过可见伪影的事故（静止态艏部青绿）就发生在这里**，恰恰没被守住。可断言的是：`geoFront(0)` 等于 `FRONT_LO - FRONT_LEAD`、`geoFront(TAU_STAR)` 等于 `FRONT_HI`、退回结束时回到 `FRONT_LO - FRONT_LEAD`、以及 `matFront(τ) - geoFront(τ)` 恒等于 `FRONT_LEAD`。
2. **`Channels::solid`** 没有断言：取值范围 $[0,1]$、静止态为 1、以及"$v$ 到顶那一刻归零"这三条都可断言。
3. **`advance` 的输入保护**：负 `frameDt`、超过 `DT_MAX` 的 `frameDt`、以及 `TIME_SCALE` 的缩放效果，都没有测。
4. **六条包络一条都没测**：`anticipation` / `stretchAmount` / `fovKick` / `shakeEnvelope` / `wireGrow` / `wireAlpha`。至少可断言"两端取值精确为 0"与"峰值时刻恰为 1"。
5. **P4 测的是算术恒等式而不是实现**（见 9.5）。
6. **着色器完全没有自测**（`filaments` 那两处转录错是靠人眼发现的）。GLSL 没有现成的断言机制，只能靠慢放目视确认，这一条短期内补不上。

其中第 1 条最值得补，因为它对应的事故真实发生过。一个可以直接加的 P8（**尚未加入代码**）：

# 第 10 段（上）· 接线：输入与时间线

这一段的代码都在活跃文件 `src/SpaceShip23.0.cpp` 的 `main` 主循环里。全段按**一帧的执行顺序**来讲，因为这里几乎所有 bug 都是"顺序写错了"而不是"公式写错了"。

## 10.1 一帧里的顺序

```
deltaTime = glfwGetTime() 的差值
processInput(window)                         （含 T 键触发与"折跃期间冻结操控"）
alpha = ship.AdvanceFixed(physAccum, deltaTime, alpha)   （定步长物理）
gWarp.cooldown 递减
if (gWarp.active)  warp::advance(tau, deltaTime)         （时间线推进 + 可能的传送）
wch = warp::sample(gWarp.tau);  solidNow;  camGate
shipModel = ship.GetModelMatrix(alpha);  shipWireModel
预备退距、拉伸与锚点
相机块（FOLLOW 时平滑跟随）
视锥剔除、阴影 pass、各绘制 pass
projection（FOV 冲击）与 view（抖动）
后处理
```

三处顺序是**承重的**，写反了画面就会错：

1. **输入在物理步进之前**。`processInput` 设的是 `targetSpeed` 这类目标量，`AdvanceFixed` 随后在同一帧把它们推向实际速度。反过来的话所有操纵会延迟一帧。
2. **传送在物理步进之后**。一次 `AdvanceFixed` 可能跑两步或更多（补帧），若传送发生在它之前，随后的积分会把刚落位的舰体继续推走。传送写的是"这一帧渲染要用的那两个字段"，所以必须在取模型矩阵之前。
3. **`wch` 在 `advance` 之后取**。钉帧那一帧 `advance` 把 τ 精确设成 `TAU_STAR`，于是 `wch.g` 逐位等于 1；若把 `sample` 挪到 `advance` 之前，那一帧取到的是**上一帧的 τ**（$g\approx0.66$），全屏白会晚一帧，而那一帧恰恰是传送帧——背景的视差跳变就会露出来。

另外要意识到一件事：**折跃时间线由渲染帧时间驱动，物理由定步长驱动**。两者只在一个地方交汇——传送那一帧由视觉时间决定，而传送本身是物理侧的一次瞬时重定位。这也是 P7 那条"实际用时落在 $[\text{T\_TOTAL},\text{T\_TOTAL}+2dt)$"的来处：视觉时间跟着帧率走，物理时间不跟。

## 10.2 T 键：一次触发、两条拒绝、一处占位

```cpp
if (glfwGetKey(window, GLFW_KEY_T) == GLFW_PRESS && !tKeyPressed)
{
    tKeyPressed = true;

    const bool busy    = gWarp.active;
    const bool cooling = (gWarp.cooldown > 0.0f);

    if (!busy && !cooling)
    {
        glm::vec3 fhat = ship.Forward();
        const float flen = glm::length(fhat);
        if (flen > 1e-6f)
        {
            fhat /= flen;                       // 单位化，delta 才等于距离
            const float dist = WARP_DISTANCE;   // 阶段 6 在此插射线-球钳制
            gWarp.delta = fhat * dist;
            gWarp.tau = 0.0f;
            gWarp.active = true;
        }
    }
}
if (glfwGetKey(window, GLFW_KEY_T) == GLFW_RELEASE)
{
    tKeyPressed = false;
}
```

- **`!tKeyPressed` 是上升沿锁存**（照抄 TAB 键那一套）。`GLFW_PRESS` 在按住 T 的每一帧都为真，没有锁存就会每帧重新触发一次。复位单独写成一条 `if (GLFW_RELEASE)`，不放进上面那个 `if` 的 `else`，因为松键与按下是两件独立的事。
- **两条拒绝条件都静默**：正在折跃（`busy`）与冷却未到（`cooling`）。这两种情况玩家自己能理解（已经在跳、还没好），播特效反而误导。红闪是留给"落点非法"的（阶段 6），那是玩家需要知道"为什么没反应"的情况。
- **先单位化再乘距离**：这样 `gWarp.delta` 的长度就等于"折跃距离"这个有物理意义的量，而不是"某个未归一化的前向量乘以 100"。`flen > 1e-6f` 是除零保护——`heading` 一直被 normalize，理论上不会退化，但除零的代价太大，值得一行。
- **`dist` 那一行是阶段 6 的预留位置**：射线与火星球求交、钳到 `D_eff`、再与 `WARP_MIN_DIST` 比较，全部插在这里。`WARP_MIN_DIST` 已经在 `Globals.h` 里等着被引用。
- 最后三行就是"启动一次折跃"的全部：`delta`（方向与距离，此刻冻结）、`tau = 0`（时钟归零）、`active = true`（跑起来）。**三行必须齐全**——少 `active` 就是"算好了不跑"，而这个错误在别处表现为"按了 T 什么都没发生"，很难指向这里。

## 10.3 折跃期间冻结操控，以及那个"位置放错了"的坑

```cpp
// 折跃期间冻结舰体控制。必须在三个模式分支之后独立判断，不能写成分支里的
// else if —— MODE_FREE 下舰体本来就不受操控，那五个目标量没有任何一处会
// 重置，会一直保留上一次在模式 2/3 里设的角速度，舰体在折跃过程中继续转，
// heading 就漂了，落点方向与视觉方向脱钩。
if (gWarp.active)
{
    ship.targetSpeed = 0.0f;
    ship.targetVerticalSpeed = 0.0f;
    ship.targetYawAV = 0.0f;
    ship.targetPitchAV = 0.0f;
    ship.targetRollAV = 0.0f;
}
```

- 归零的是**五个目标量**，不是实际速度。物理侧会按 `decel` 与 `angularAccel` 平滑地把实际值推向 0，所以舰体是"松开油门、慢慢停转"，不是瞬停——这一段是刻意的：瞬停会看起来像被冻住。
- **它必须独立于三个模式分支**。写成某个分支里的 `else if` 就只覆盖模式 2/3；`MODE_FREE` 下舰体本来就不受操控，那五个目标量**没有任何一处会被重置**（模式 1 的分支只动相机），于是它们保留着上一次在模式 2/3 里设的角速度，舰体在折跃过程中继续转，`heading` 漂掉，落点方向与视觉方向脱钩。这个错误真的发生过，当时的写法就是把它塞进了 `else`。
- 冻结的代价要知道：目标速度归零不等于速度归零，蓄能期舰体仍然带着原速度前飘（最坏约 13 世界单位，见第 8 段），而位移是加在**传送那一帧**的位置上的，所以落点会随之前移。这是"冻结输入但保留惯性"的必然结果，也是"蓝图跟着一起飘"那条设计的物理来源。

## 10.4 时间线推进与传送

```cpp
if (gWarp.cooldown > 0.0f)
{
    gWarp.cooldown -= deltaTime;
    if (gWarp.cooldown < 0.0f) gWarp.cooldown = 0.0f;
}

if (gWarp.active)
{
    const warp::Step wstep = warp::advance(gWarp.tau, deltaTime);

    if (wstep.teleport)
    {
        ship.WarpTo(ship.position + gWarp.delta);

        if (currentMode == MODE_FOLLOW)
        {
            camera.Position += gWarp.delta;
            // 阻尼 mix 不跳过：目标锚点 K* 同时也移动了同一个 delta，
            // 误差 e = K* - K 不变，递推原样继续（计划书 §5.2）。
        }

        gWarp.cooldown = WARP_COOLDOWN;   // 冷却自 TAU_STAR 起算
    }

    if (wstep.finished)
    {
        gWarp.active = false;
        gWarp.tau = 0.0f;
    }
}
```

- 冷却的递减放在 `if (gWarp.active)` **外面**：冷却与时间线互不依赖，时间线跑完（约 1.25 s）之后冷却还有 4 秒多要继续走。
- `advance` 收的是**裸 `deltaTime`**。钳到 `DT_MAX`、乘 `TIME_SCALE` 都在 `advance` 内部完成（第 4 段）——"对时间的加工只有一处"，这里刻意不再夹一层。
- `wstep.teleport` 那一帧做三件事，缺一不可：
  - `ship.WarpTo(ship.position + gWarp.delta)`：注意加的是**传送那一帧的位置**，不是按键那一帧的位置（第 8 段）。
  - FOLLOW 模式才平移相机。注释解释了为什么"阻尼 mix 不用跳过"：跟随相机每帧朝目标锚点 $K^*$ 做一次 mix，传送让舰体与 $K^*$ **同时**移动同一个 `delta`，于是误差 $e = K^* - K$ 不变，递推原样继续。**这正是命题 2 在代码里的落点**：不变的不是"相机的位置"，而是"相机与舰体的相对关系"。
  - 冷却重置为 `WARP_COOLDOWN`。放在传送帧而不是按键帧，是因为按键之后到传送之间还有 0.65 s 的时间线要走，冷却从"跳成功那一刻"起算才符合直觉。
- `wstep.finished` 的两行赋值就是"停机态"的全部实现：`active = false` 让时间线停下，`tau = 0` 让所有通道回到常规值（第 1 段的自检问题 2）。**不需要任何别的复位代码**——这也是"把效果做成一条以 τ 为参数的曲线"的回报。

## 10.5 三个派生量与门控

```cpp
const warp::Channels wch = warp::sample(gWarp.tau);
const float solidNow = wch.solid * (1.0f - warp::geoFront(gWarp.tau));
const float camGate  = (currentMode == MODE_FOLLOW) ? 1.0f : 0.0f;
```

- `wch` 是**唯一**一处把 τ 翻译成权重的地方（第 3 段），所有 pass 都读它。它的位置在 `advance` 之后、传送之后（见 10.1 的第 3 条）。
- `solidNow` 给阴影 pass 用：`wch.solid` 是"舰体实体度"，乘上 $1-\text{geoFront}$ 是因为真实溶解是逐像素 discard，通道权重并不知道前沿走到哪了。
- `camGate` 是三种**相机侧**效果的共同门控：全屏闪现、FOV 冲击、抖动。它们的共同点是"卖相机随舰体一起被推走"的位移感，而只有 FOLLOW 模式的相机锚在舰体上；模式 1/2 的相机是玩家自己的（固定 / 由 WASD 驱动），推它 100 单位是纯粹的错。三处使用点分别乘以它，是"一个判据只写一次"的写法。

# 第 10 段（下）· 接线：模型矩阵、相机与投影

## 10.6 模型矩阵链：前乘与后乘的区别

```cpp
glm::mat4 shipModel = ship.GetModelMatrix(alpha);   // T(RenderPosition) · R(RenderHeading) · S(0.0005)
const glm::mat4 shipWireModel = shipModel;          // 快照：不含预备退距、不含拉伸

// 预备退距：前乘
shipModel = glm::translate(glm::mat4(1.0f), -ship.RenderForward(alpha) * backAmount) * shipModel;

// 拉伸：后乘（物体空间夹心）
shipModel = shipModel
    * glm::translate(glm::mat4(1.0f), glm::vec3(0.0f,  yAnchor, 0.0f))
    * glm::scale(glm::mat4(1.0f), glm::vec3(1.0f, stretch, 1.0f))
    * glm::translate(glm::mat4(1.0f), glm::vec3(0.0f, -yAnchor, 0.0f));
```

在列向量约定（$v' = M v$，矩阵从右往左作用）下，**前乘是在父空间（世界）里作用，后乘是在物体空间里作用**。这两行正好各用一种，理由是语义而不是风格：

- **预备退距用前乘**。它是"沿航向在世界里后退 1.5 单位"，方向由 `RenderForward(alpha)` 给出，那是个**世界向量**。写成 `T(世界位移) * shipModel` 时，这层平移作用在已经旋转、缩放好的结果上，就是在世界里平移整艘船。
- **拉伸用后乘**。它沿的是**机体纵轴**，而机体纵轴在物体空间里就是 $Y$。写成 `shipModel * [T(a) S_y T(-a)]` 时，夹心先于旋转作用，作用在原始的模型坐标上，所以 $a$ 必须是物体空间的 $\pm 53668$。

**两者写反会怎样**，这是最值得记住的一对反例：

- 拉伸写成前乘，夹心就作用在**世界 $Y$ 轴**上。舰体一般不是沿世界 $Y$ 飞的，于是拉伸方向会随航向乱变（横着拉长、竖着拉长都出现），而且 53668 这个量级直接作用在世界坐标上，舰体会飞出屏幕。
- 退距写成后乘，`RenderForward(alpha)` 这个**世界向量**会被当作物体空间的固定方向来解释，只在航向恰好等于单位阵时才正确。舰体一转，退距方向就错。

两个 `if` 判据都值得注意：`if (backAmount > 0.0f)` 与 `if (stretch > 1.0f)`。在非蓄能期与静止态，`anticipation` 与 `stretchAmount` 返回的是**精确的 0**（两个函数都有 `return 0.0f` 的显式分支），所以浮点相等比较在这里是安全的，而且能整段跳过矩阵乘法。若哪天把这两个函数改成"返回很小的值"，判据就得换成阈值。

**同一帧里两份矩阵，语义不同**，这是折跃接线的核心对照：

| 矩阵 | 内容 | 用在哪 |
|---|---|---|
| `shipWireModel` | 只有 $T \cdot R \cdot S$，即舰体的最终姿态 | 目的地蓝图、传送后的线框 |
| `shipModel` | 再叠上预备退距与拉伸 | 舰体 PBR、电流外壳、阴影投影 |

影子必须与投出它的实体同形，所以阴影用 `shipModel`；而线框与蓝图是"舰体的最终形状"，所以用 `shipWireModel`。外壳贴在表面上、必须跟着形变走，所以也用 `shipModel`。

## 10.7 相机块

```cpp
if (currentMode == MODE_FOLLOW) {
    glm::vec3 fwd = ship.RenderForward(alpha);
    glm::vec3 target = ship.RenderPosition(alpha) - fwd * followDistance + glm::vec3(0.0f, followHeight, 0.0f);

    float t = glm::clamp(followSmooth * deltaTime, 0.0f, 1.0f);
    camera.Position = glm::mix(camera.Position, target, t);

    glm::vec3 toShip = glm::normalize(ship.RenderPosition(alpha) - camera.Position);
    glm::quat orbitRot = glm::angleAxis(glm::radians(orbitYaw),   glm::vec3(0.0f, 1.0f, 0.0f)) *
                         glm::angleAxis(glm::radians(orbitPitch), glm::vec3(1.0f, 0.0f, 0.0f));

    camera.Front = orbitRot * toShip;
    camera.Right = glm::normalize(glm::cross(camera.Front, glm::vec3(0.0f, 1.0f, 0.0f)));
    camera.Up    = glm::normalize(glm::cross(camera.Right, camera.Front));
}
```

- **一律用 `RenderPosition(alpha)` / `RenderForward(alpha)`，不用 `position` / `Forward()`**。相机、阴影 pass、视锥剔除、舰体 PBR 必须共用**同一份插值位姿**；只要有一处读的是未插值的 `position`，那两者就会差 $(1-a)$ 个物理步，症状是"影子滑开、相机相对舰体抖"。这是"同一渲染帧内飞船姿态只算一次"那条教训的具体落点，而 `alpha` 来自 `AdvanceFixed`，全帧共享。
- 目标点是"后方 `followDistance = 80`、上方 `followHeight = 25`"。注意高度那一项是**世界空间**的 `(0, followHeight, 0)`，不是沿机体上方向后上方——所以舰体滚转时相机不跟着滚，读起来更稳。这是有意的选择，不是漏写。
- `t = clamp(followSmooth * deltaTime, 0, 1)` 是一阶指数逼近的离散近似，`followSmooth = 2.0` 对应约 0.5 s 的时间常数；`clamp` 到 1 保证大 `deltaTime` 时直接贴上去而不过冲。
- 朝向每帧重建：`toShip` 由当前位置算，`Front` 叠上环视偏移，`Right` 与 `Up` 由 `Front` 与**世界 up** 重新叉乘得到。这样不会累积滚转误差，也不会因为 `mix` 的插值位置而产生"看着舰体的侧后方"。
- **与命题 2 的关系（这一段是它在代码里的证明）**：传送那一帧，`RenderPosition(alpha)` 跳了 `delta`，同时 `camera.Position` 也加了同一个 `delta`。于是 `target` 与 `camera.Position` 一起平移，`mix` 的输入与输出同时平移，递推关系不变，**相机与舰体的相对位置精确保持**。所以 `toShip` 不变、`view` 矩阵只是平移了 `delta`，舰体的屏幕姿态一个像素都不动，动的只有背景。背景会跳几十度，这才是全屏白闪存在的唯一理由。

## 10.8 投影与抖动

```cpp
glm::mat4 projection = glm::perspective(
    glm::radians(camera.Fov - warp::FOV_KICK * warp::fovKick(gWarp.tau) * camGate),
    aspect, 0.1f, 2000.0f);

const glm::vec3 camShake =
    ship.RenderForward(alpha) * (warp::SHAKE_AMT * warp::shakeEnvelope(gWarp.tau) * camGate);
camera.Position += camShake;
glm::mat4 view = camera.GetViewMatrix();
camera.Position -= camShake;
```

- **FOV 冲击是减号**：视场角变小，画面被推远（长焦压缩），读作一次推镜。乘 `camGate` 保证只在 FOLLOW 模式生效。
- **抖动是沿航向的位移脉冲，不是随机噪声**。方向取 `RenderForward(alpha)`，大小是 `SHAKE_AMT · shakeEnvelope(τ) · camGate`。沿航向的位移读起来是"被撞了一下"，而随机抖动读起来是"镜头在抖"，两者完全不同。
- **加偏移、取 `view`、再减回去**，绝不能把偏移留在 `camera.Position` 里。原因有二：跟随阻尼下一帧会从"被抖过的位置"起步，抖动会被记住并且逐帧累积；而且"相机与舰体的距离"会被污染，第 6 段那条距离不变式的验收就失效了。这里是**用同一个变量、同一次计算**做的保存与恢复——这一点要刻意保持，别在中间重新算一遍。它与 AGENTS 里那条 GL 状态教训是同一个模式的两面：那条错在"按假设还原"（对从未开启过的状态调 `glEnable` 不是还原而是首次开启），这条对在"拿着真值还原"。
- 顺序上还有两点：`view` 必须在抖动**之后**取（否则白算）；阴影 pass 用的是自己的 6 面矩阵与 `shadowProj`，**不受 `view` 影响**，所以抖动不会让影子跟着晃——这是对的，影子是世界空间里的事实。
- 剔除（`RockViewFrustumCull`）发生在抖动**之前**，用的是基准 FOV 与未抖动的相机位置。当前两者都是"安全方向"：FOV 冲击只会让视锥**变窄**，判定用的视锥比实际需要的更宽（保守），不会误剔；相机偏移只有 0.30 世界单位。但这条结论依赖"FOV 冲击只收紧"与"抖动幅度很小"两个前提——若哪天把冲击改成放大、或把幅度加大，这两处要重新评估。

# 第 10 段（补）· 落点冻结：从 delta 到 target

这一节是第 10 段的补充。起因是阶段 6（落点合法性）落地之后暴露出的量级问题：判定在按键帧算，落点却在传送帧才确定，两者之间隔了 0.65 s 的蓄能期。补充里把**旧版**（按增量传送，用了很久、本身完全正确）与**新版**（冻结落点）并排记下来。

活跃文件现在是 `src/SpaceShip23.A.cpp`（阶段 6 与红闪都在这一版里），它由 `23.0` 顺延而来，第 10 段里的行号锚点对两版都适用。

## 10.9 旧版：按增量传送

```cpp
// 按键那一帧：只冻结"位移向量"
gWarp.delta = fhat * dist;
gWarp.tau = 0.0f;
gWarp.active = true;

// 传送那一帧：把增量加在【当时的位置】上
ship.WarpTo(ship.position + gWarp.delta);
if (currentMode == MODE_FOLLOW) camera.Position += gWarp.delta;

// 目的地蓝图：从"当前姿态"前移 delta
glm::translate(glm::mat4(1.0f), gWarp.delta) * shipWireModel
```

- **语义**：`delta` 是位移向量，在按键帧冻结；传送时把它加在**传送那一帧的位置**上。落点从来不是一个被记住的点，而是"那一帧算出来的点"。
- **它为什么一直是对的**：命题 2 只要求"舰体与相机加同一个向量"，至于这个向量加在哪个基点上，与那条性质无关。所以这套写法在很长一段时间里完全成立，三个消费者（传送、相机、蓝图）也天然一致——它们都用同一个 `delta`。
- **唯一的代价**：真实落点是 `position(τ*) + delta`，而 `position(τ*)` 已经因为蓄能期的惯性前飘往前挪了。输入被冻结但速度还在（`decel = 30`，初速最大 30，0.65 s 内漂 $30 \times 0.65 - 15 \times 0.65^2 \approx 13.2$ 单位），于是：
  - **射程偏大**：从按键那一刻算起的总位移是 `dist + 漂移`，最多比名义值多 13%（100 变 113）。
  - **判定点与落点不同**：合法性判定用的是按键帧的 `position`，真实落点却在那之前 13 个单位处，所以钳出来的"舰首停在球面前 5% 半径"会被这段漂移吃掉一部分。
- 这两条都不是 bug，是"增量式落点"这个语义的固有性质。在阶段 6 之前它们不影响任何观感，所以一直没有暴露。

## 10.10 新版：冻结落点

`Globals.h` 里保留旧字段作留档，新字段写在旁边：

```cpp

    glm::vec3 target = glm::vec3(0.0f);    // 【当前】冻结落点：按键帧定死，传送那一帧直接用它
```

按键帧把落点一次算清：

```cpp
                    // 落点在按键帧一次定死。传送那一帧直接用这个点，于是"从按键那一刻
                    // 算起的总位移"精确等于 dist —— 蓄能期的惯性前飘不再改变落点，
                    // 落点合法性判定与最终落点也从此是同一个量。

```

传送帧改用"实际位移向量"，三个消费者仍然共用同一个量：

```cpp

                // 命题 2（舰体屏幕姿态不变、只有背景在跳）才继续精确成立。
                const glm::vec3 jump = gWarp.target - ship.position;
                ship.WarpTo(gWarp.target);          // 旧版：ship.WarpTo(ship.position + gWarp.delta);

                if (currentMode == MODE_FOLLOW)
                {
                    camera.Position += jump;        // 旧版：camera.Position += gWarp.delta;
                    // 阻尼 mix 不跳过：目标锚点 K* 同时也移动了同一个 jump，
                    // 误差 e = K* - K 不变，递推原样继续（计划书 §5.2）。
                }
```

蓝图的矩阵基点也跟着换：

```cpp
            warpWireShader.setMat4("model",
                glm::translate(glm::mat4(1.0f), gWarp.target - ship.RenderPosition(alpha)) * shipWireModel);
            // 旧版：glm::translate(glm::mat4(1.0f), gWarp.delta) * shipWireModel);
```

用 `RenderPosition(alpha)` 而不是 `position` 是必需的：插值位姿可能落后一个物理步，但这里是"目标减当前"，两者一减就抵消，于是蓝图**永远精确落在目标点上**，与它当前插值到哪儿无关。到了 τ\* 那一帧，`RenderPosition(alpha)` 已经是落点本身，平移量为 0，所以蓝图与传送后那份线框逐位重合——这正是第 7 段花了好几轮才收敛到的那个性质，换成冻结落点之后它变成自动成立的。

**顺带修正的两件事**：射程精确等于 `dist`；判定点与落点重新是同一个量，钳出来的净空不再被前飘吃掉。

**一个新的边界情形**：若钳制结果恰好等于 `WARP_MIN_DIST = 10` 而漂移是 13.2，那么 τ\* 时舰体已经在落点**前方**约 3 单位，这一跳会变成一次微小的后退。要消除它，把 `WARP_MIN_DIST` 提到大于最大漂移即可（13.2，取 20 保险）。

# 第 11 段 · 五个绘制 pass 与 GL 状态纪律

## 11.1 绘制顺序与共同约定

一帧里折跃相关的绘制按这个顺序发生：

```
1. 舰体 PBR（含溶解与白化）    glCullFace(GL_BACK) 之后 spaceship.Draw(spaceshipShader)
2. 电流外壳                    if (wch.c > 0.001f)
3. 目的地蓝图                  if (gWarp.active && gWarp.tau < warp::TAU_STAR)
4. 线框                        if (wireAlpha > 0.001f && gWarp.tau >= warp::TAU_STAR)
5. 全屏闪现                    if (flashAmount > 0.0f)
之后进入 PostProcessing（bloom / lens flare / tonemap / gamma）
```

顺序的理由：不透明的舰体先画（它写深度，参与后面所有的遮挡判断）；三个加法混合的效果随后叠加；全屏闪现在**最后**，这样它才是"盖在所有东西之上的一层白"；全部都在后处理之前，所以闪白与白化（`uWhiteK = 6.0`）都会进 bloom，观感上是"过曝"而不是"贴一张白纸"。

三个加法 pass 的共同写法：`glEnable(GL_BLEND)` 配 `glBlendFunc(GL_ONE, GL_ONE)`（加法），加上 `glDepthMask(GL_FALSE)`（读深度、不写深度），所以它们既不遮挡后面的东西，也不互相遮挡。

## 11.2 舰体 PBR pass：uniform 清单与"物体空间量"

```cpp
spaceshipShader.setMat4("model", spaceshipModel);       // = shipModel（含退距与拉伸）
spaceshipShader.setMat3("normalMatrix", glm::transpose(glm::inverse(glm::mat3(spaceshipModel))));
spaceshipShader.setFloat("rimStrength", 0.6f * (1.0f + 4.0f * wch.c));   // 蓄能期放大边缘光
spaceshipShader.setFloat("uVanish", wch.v);
spaceshipShader.setFloat("uWhiteK", 6.0f);

const float frontGeo = warp::geoFront(gWarp.tau);
spaceshipShader.setFloat("uFrontRev", (gWarp.tau > warp::T_WIRE_END) ? 1.0f : 0.0f);
spaceshipShader.setFloat("uFrontMat", warp::matFront(gWarp.tau));
spaceshipShader.setFloat("uFrontGeo", frontGeo);

spaceshipShader.setFloat("uAxisMinY", shipAxisMinY);             // 物体空间！
spaceshipShader.setFloat("uAxisMaxY", shipAxisMaxY);
spaceshipShader.setFloat("uObjRadius", shipBoundR / 0.0005f);    // 把世界半径折回物体空间
spaceshipShader.setFloat("uNoiseW", warp::NOISE_W);
spaceshipShader.setFloat("uNoiseFreq", 9.0f);
spaceshipShader.setFloat("uEdge", 0.06f);
spaceshipShader.setVec3("uDissolveColor", glm::vec3(0.25f, 0.95f, 0.80f));
```

这一块最值得记住的是**单位**。着色器里的溶解与拉伸全部建立在**物体空间坐标**上（顶点着色器把 `aPos` 原样传进 frag），所以：

- `uAxisMinY` / `uAxisMaxY` 必须是模型顶点的原始坐标（$\pm53668$），**不能乘 `0.0005`**。乘了之后前沿会缩到两千分之一，舰体永远停在"全剥完"的状态。
- `uObjRadius` 反过来：`shipBoundR` 是世界单位的包围半径，而着色器要用它归一化物体坐标（`q = ObjPos / uObjRadius`），所以要把世界半径**除回**模型缩放，得到 53668 量级的那个数。
- 这两处任一搞错，症状都不是"稍微不对"而是画面整体崩，所以单列出来。

另外两点：

- `uFrontRev` 是 **0/1 布尔量**，由 `gWarp.tau > warp::T_WIRE_END` 决定，就是第 5 段那个"返程镜像坐标"开关，切换点正是"几何退回起点"那一帧。写成 0/1 而不是两个 shader，是为了不再多一套 `uFrontGeo` / `uFrontMat` 的命名。
- `rimStrength` 借 `wch.c` 放大，是阶段 0 的占位留下的，后来没有拆——因为"蓄能期舰体边缘泛起蓝光"正是要的观感，于是它从占位变成了正式效果。这类"临时占位最后成了设计"的地方要标出来，否则后人会当成遗漏。

## 11.3 电流外壳：贴在表面上的一层光

```cpp
if (wch.c > 0.001f)
{
    glEnable(GL_BLEND);
    glBlendFunc(GL_ONE, GL_ONE);      // 加法混合
    glDepthMask(GL_FALSE);            // 不写深度，别挡住后面要画的东西
    glCullFace(GL_FRONT);             // 只画背面：读起来才是"裹住"而不是"镀一层"

    warpShellShader.use();
    warpShellShader.setMat4("model", spaceshipModel);        // 与 PBR pass 同一份
    warpShellShader.setVec3("uShellColor", glm::vec3(0.35f, 0.75f, 1.0f));
    warpShellShader.setFloat("uShellStrength", wch.c * 2.0f);
    warpShellShader.setFloat("uShellWorld", shipBoundR * 0.03f);
    warpShellShader.setFloat("uObjRadius", shipBoundR / 0.0005f);
    warpShellShader.setFloat("uTime", currentFrame);
    spaceship.Draw(warpShellShader);

    glCullFace(GL_BACK);
    glDepthMask(GL_TRUE);
    glDisable(GL_BLEND);
    glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);
}
```

- `if (wch.c > 0.001f)` 让非蓄能期**一次绘制都不发生**，常态零开销。
- 外壳用 `spaceshipModel`（含拉伸），因为它贴在舰体表面上，不跟着形变走就会和舰体脱开——这与线框反过来用不含拉伸的 `shipWireModel` 是同一个判据的两面：**贴体的跟着形变，独立于形变的（蓝图）不跟**。
- `glCullFace(GL_FRONT)` 那一行**是空操作**：本工程从未 `glEnable(GL_CULL_FACE)`，所以它没有任何效果。注释里"只画背面"的描述与实际不符（不影响观感），但别据此推断"背面被剔掉了"。
- `uShellWorld = shipBoundR * 0.03f` 是外壳沿法线的世界空间厚度，约半径的 3%。
- `uTime = currentFrame`（`glfwGetTime()`）说明**细丝的流动用墙钟**，不是 τ。所以把 `TIME_SCALE` 置 0.1 慢放时，时间线慢了十倍而细丝仍在原速流动。要做"整体慢放"就得把这个基准也换成 τ 或乘上 `TIME_SCALE`——当前是有意取舍（外壳的流动感与折跃节奏无关），但要知道自己选了什么。

## 11.4 目的地蓝图与线框：同一套 shader，两份矩阵

两块代码的差别只有三处：

| | 目的地蓝图 | 传送后的线框 |
|---|---|---|
| 条件 | `gWarp.active && gWarp.tau < warp::TAU_STAR` | `wireAlpha(tau) > 0.001f && gWarp.tau >= warp::TAU_STAR` |
| 矩阵 | `T(gWarp.delta) * shipWireModel` | `shipWireModel` |
| 用途 | 在落点预先把骨架画出来 | 舰体到达之后那副骨架本身 |

其余全部相同：同一个 `warpWireShader`、同一条 `wireGrow`、同一条 `wireAlpha`、同样的颜色与线宽、同样只读深度不写深度。**两块没有合并**，因为判据语义不同（"还没传送"与"已经传送"）且矩阵不同；硬合并成 `active && (tau < TAU_STAR || tau >= TAU_STAR)` 只会得到一句没有信息量的话。

`T(gWarp.delta) * shipWireModel` 这个矩阵值得再强调：它是"舰体当前姿态整体前移 `delta`"。传送那一帧 `shipWireModel` 本身已经是落点姿态，所以两块在那一帧给出**逐位相同的世界位姿**——形状、位置、亮度三者相同，于是"两次绘制"在观感上是一次。

两块都不写深度：骨架是"投影"而不是实体，不该挡住随后灌进来的材质。

## 11.5 全屏闪现：唯一的屏幕空间 pass

```cpp
const float flashAmount = wch.g * camGate;

if (flashAmount > 0.0f)
{
    glEnable(GL_BLEND);
    glBlendFunc(GL_ONE, GL_ONE);        // 加法混合
    glDisable(GL_DEPTH_TEST);           // 全屏 quad 不需要深度
    glDepthMask(GL_FALSE);

    glm::vec2 flashCenter(0.0f);
    const glm::vec4 clip = projection * view * glm::vec4(ship.RenderPosition(alpha), 1.0f);
    if (clip.w > 1e-4f) flashCenter = glm::vec2(clip.x / clip.w, clip.y / clip.w);

    warpFlashShader.use();
    warpFlashShader.setFloat("uFlash", flashAmount);
    warpFlashShader.setFloat("uFlashBase", 6.0f);
    warpFlashShader.setFloat("uFlashCore", 10.0f);
    warpFlashShader.setVec2("uFlashCenter", flashCenter);
    glBindVertexArray(quadVAO);
    glDrawArrays(GL_TRIANGLES, 0, 6);

    glEnable(GL_DEPTH_TEST);
    glDepthMask(GL_TRUE);
    glDisable(GL_BLEND);
    glBlendFunc(GL_SRC_ALPHA, GL_ONE_MINUS_SRC_ALPHA);
}
```

- **它是唯一一个全屏 pass**：不画几何，只往整张图上加亮度。`uFlashBase = 6.0` 是整屏都会拿到的基础亮度，`uFlashCore = 10.0` 是圆心附近的额外核心项。两个数都在 HDR 范围（远超后处理阈值），所以必然进 bloom，观感是"过曝"而不是"蒙一层白纱"。
- **圆心**：把舰体的世界位置用**同一帧的** `projection` 与 `view` 投到 NDC。必须用这两个矩阵而不是另算一套，因为 `projection` 里已经含 FOV 冲击、`view` 里已经含抖动，圆心必须与画面上舰体真正的位置一致。
- `if (clip.w > 1e-4f)` 是 **NaN 闸门**：`clip.w` 接近 0 意味着点在相机平面附近甚至后面，透视除法会给出 inf 或 NaN；NaN 进到 `uFlashCenter` 会让闪现变成一片黑或一片花，而且症状离肇事点很远。`w` 太小时保持 `(0,0)`，宁可圆心偏掉。
- **深度测试关掉**：它是最后画的，前面所有东西已经在颜色缓冲里。退出时把 `GL_DEPTH_TEST`、`GL_DEPTH_MASK` 与混合三项都还原。
- `flashAmount = wch.g * camGate`：`camGate` 让模式 1/2 完全不画（那里的相机不动、世界固定物的投影逐像素不变，没有跳变要遮；而且那两种视角恰恰是想看清折跃的视角）。模式 1/2 下"舰体自己在屏幕上换位置"这一下由 `u_v` 白化负责。

## 11.6 阴影 pass 的舰体门控与一个待评估的半径问题

```cpp
if (solidNow > 0.5f)
{
    simpleDepthShader.setMat4("model", shipModel);      // 含退距与拉伸
    int sf[6]; int sn = AssignCasterFaces(pointSunPositions, ship.RenderPosition(alpha), shipBoundR, sf);
    for (int k = 0; k < sn; ++k) { ... spaceship.Draw(simpleDepthShader); }
}
```

- 门限 `solidNow > 0.5f` 把"深度 pass 做不了半透明"挡在门外：舰体已经看不清了，影子就不该还在。数值上它在白化到顶（τ = 0.60）那一刻关闭，在返程 `geoFront` 降到 0.5 时（约 τ = 1.10）重新打开。
- 模型矩阵用 `shipModel`：影子必须与投出它的实体同形，预备退距与拉伸都要带上。
- **待评估**：`AssignCasterFaces` 收的是 `shipBoundR`，那是**未拉伸**的包围半径；而同一处的 `shipModel` 已经含拉伸。返程尾段（约 τ = 1.10 到 1.25）拉伸还有 1.24 降到 1.0，半径最多低估约 24%。那个函数的判据是"这个投影者能投到哪几个面"，它把物体当球处理，半径偏小就可能漏掉某个面，症状是那一面上的影子整块缺失。稳态飞行不受影响（那时 `stretch` 精确等于 1.0）。
  一行修法：把半径乘上当前拉伸量，`AssignCasterFaces(..., shipBoundR * stretch, sf)`。`stretch` 在同一作用域可见，且非折跃期精确等于 1.0，所以对常规飞行零影响。这类问题属于"保守判据 + 正确包围体"那一类：**判据没错，是喂给它的包围体不保守**。

## 11.7 GL 状态纪律

这几段代码合起来能总结出三条规矩：

1. **只碰自己需要的状态。** 每个 pass 进来只开关自己真正要用的那几项，退出时逐项还原（混合开关、混合函数、深度写、剔除面）。
2. **还原要拿真值，不能凭假设。** 对工程从未设置过的状态，`glEnable(...)` 不是还原而是**首次开启**。要么用 `glIsEnabled(...)` 查真值再还原，要么干脆不碰。
3. **不要"顺手帮忙"。** 任何"我觉得这里应该是这个状态"的写法，先确认工程是否设置过它。

这三条是从一次真实事故里总结的：线框 pass 结尾曾写过 `glEnable(GL_CULL_FACE)` 想还原剔除状态，可本工程从未启用过剔除，于是**第一次折跃之后剔除被永久打开，太阳的日冕整块消失**。症状离肇事点极远——排查时先怀疑的是太阳那一段。现在那两行是注释状态，注释里写着"两面都画"，这也是本工程所有 `glCullFace(...)` 都是空操作的原因。

反面的正面例子就是第 10 段那个抖动：它加偏移、取 `view`、再用**同一个变量**减回去，是"拿着真值还原"，所以正确。

# 第 12 段（上）· 舰体与外壳的着色器

## 12.1 `spaceship_ver3.0.shader`：一行输出撑起整套溶解

```glsl
#version 330 core
layout (location = 0) in vec3 aPos;
layout (location = 1) in vec3 aNormal;
layout (location = 2) in vec2 aTexCoords;

out vec2 TexCoords;
out vec3 WorldPos;
out vec3 Normal;
out vec3 ObjPos;                      // 折跃加的那一行

uniform mat4 projection;
uniform mat4 view;
uniform mat4 model;
uniform mat3 normalMatrix;

void main()
{
    TexCoords = aTexCoords;
    WorldPos  = vec3(model * vec4(aPos, 1.0));
    Normal    = normalMatrix * aNormal;
    ObjPos    = aPos;                 // 原样的物体空间坐标
    gl_Position = projection * view * vec4(WorldPos, 1.0);
}
```

整个 `3.0` 版本相对 `2.0` 的差别就这两行。它们为什么必须加在**顶点**着色器里：片元着色器手上只有插值后的 `WorldPos` 与 `Normal`，要反推物体空间坐标就得传一个逆模型矩阵、逐片元做一次逆变换——既贵又在数值上更差（逆矩阵乘插值后的世界坐标，误差比直接插值物体坐标大）。把一个 `aPos` 直传下去，代价只是一个 varying。

两处细节：

- `Normal = normalMatrix * aNormal` **不在这里归一化**，交给后面的 `getNormalFromMap()`。`normalMatrix` 由 CPU 传进来，是 $\big(M_{3\times3}\big)^{-\mathsf T}$。**拉伸是非均匀缩放**，所以这个矩阵是必需的：若直接拿 `model` 去变换法线，拉长方向上的法线会被拉歪，光照会跟着错。这也是"拉伸只进模型矩阵、不进 position"之外的第二个理由——模型矩阵是唯一被正确变换的那一份。
- `ObjPos = aPos` 是**未经任何变换**的模型顶点坐标，量级 $\pm53668$。它旁边那些注释掉的 `Tangent` 行与折跃无关，是法线贴图的存档。

## 12.2 `spaceship_frag3.0.shader` 的折跃部分

### 12.2.1 uniform 与命名

```glsl
uniform float uVanish;         // u_v，整体白化强度
uniform float uWhiteK;         // 白热系数 K
uniform float uFrontMat;       // 材质剥离前沿 = warp::matFront(tau)
uniform float uFrontGeo;       // 几何剔除前沿 = warp::geoFront(tau)
uniform float uAxisMinY;       // 模型局部 Y 的最小值（机头在这一端）
uniform float uAxisMaxY;       // 模型局部 Y 的最大值
uniform float uObjRadius;      // 归一化半径（与外壳 pass 同值）
uniform float uNoiseW;         // 噪声抖动权重 = warp::NOISE_W
uniform float uNoiseFreq;      // 噪声空间频率
uniform float uEdge;           // 切口发光带宽
uniform vec3  uDissolveColor;  // 溶解/合成的效果色
uniform float uFrontRev;       // 0=去程；1=返程坐标镜像
```

命名规则值得记：`u` 前缀 + **注释里写明它对应 `Warp.h` 的哪个量**。这样调参时不用猜"这个 uniform 是哪个通道"。凡是直接从 `Warp.h` 取的（`uNoiseW`、两条前沿），注释里都写了等号右边的来源；凡是观感常数（`uWhiteK`、`uNoiseFreq`、`uEdge`）就在 cpp 里写死——**能派生的绝不写死，观感常数绝不派生**，这条线在这里划得很清楚。

### 12.2.2 溶解块

```glsl
vec3  q  = ObjPos / max(uObjRadius, 1e-3);
float g  = (ObjPos.y - uAxisMinY) / max(uAxisMaxY - uAxisMinY, 1e-6);

float gt = g + uNoiseW * (noise3(q * uNoiseFreq) - 0.5);
float h  = mix(gt, 1.0 - gt, uFrontRev);

if (h < uFrontGeo) discard;                       // 几何已剔除

float stripped = 1.0 - smoothstep(uFrontGeo, uFrontMat, h);

albedo    = mix(albedo,    uDissolveColor * 0.15, stripped);
metallic  = mix(metallic,  0.0,  stripped);
roughness = mix(roughness, 1.0,  stripped);
N         = mix(N, normalize(Normal), stripped);

float band = 1.0 - smoothstep(0.0, uEdge, abs(h - uFrontGeo));
float win  = smoothstep(0.0, 0.05, uFrontGeo) * smoothstep(0.0, 0.05, 1.0 - uFrontGeo);
vec3  warpGlow = uDissolveColor * band * win;
```

数学部分第 5 段已经推过，这里只讲**着色器一侧**的取舍：

- 两处 `max(..., 1e-3)` / `max(..., 1e-6)` 是除零保护。轴跨度是 107337，`1e-6` 这个下限永远不会触发，但一旦有人把模型换成退化的，它会挡住 NaN 扩散到整屏——**便宜且永远不该省**。
- **`discard` 放在最前面**：被剔除的片元直接退出，不做后面的采样与光照。溶解最深的那些像素正是数量最多的，这一行的顺序直接决定开销。
- `stripped` 一次改动**四个量**，这是"剥掉材质"读起来像裸结构而不是像变暗的原因：贴图细节丢掉（albedo 压到溶解色的 15%）、金属度归零、粗糙度拉满、法线换回几何法线。任何一条单独做都不成立——只压暗会像阴影，只换法线会像法线贴图坏了。
- `win` 的两端窗口仍然成立，因为第 5 段的镜像不改变 `uFrontGeo` 的取值范围（$[-0.185, 1.125]$ 映射到自身）。
- **切口发光由 `uVanish` 驱动**：`color += warpGlow * uVanish;` 在文件后半段。也就是说这条切口的亮边只在**隐没段**可见；抵达段的 `u_v` 已经是 0，所以返程那条自艏向艉扫过的边界是**不发光**的。这是当前的设计结果，不是漏写。若想让"从头部先抵达"更醒目，把乘数改成 `max(uVanish, 某条实体化权重)` 即可——但那条权重（`u_a`）目前没有消费者，得先把它接上。

### 12.2.3 白化

```glsl
// 整体白化：u_v 冲到 1 时整艘舰变成 uWhiteK 倍的白，远超 bright pass 阈值、必然进 bloom
FragColor = vec4(mix(color, vec3(uWhiteK), uVanish), 1.0);
```

- 它作用在**最终颜色**上（菲涅尔边缘光与切口发光都加完之后），所以整个片元一起烧白，不会留下"亮边没被烧掉"的破绽。
- `uWhiteK = 6.0` 大于 1，目的是**超过 bright pass 阈值**：这样白化不是"变白"而是"进 bloom 溢出来"，读作烧成光。
- 注意文件里那两行注释掉的 HDR tonemap 与 gamma——它们被搬到后处理里做了，所以这个 shader 输出的是 **HDR 值**。这也是 `uWhiteK = 6.0` 这种"不合法颜色"能work的前提。

### 12.2.4 噪声函数

```glsl
float hash13(vec3 p)
{
    p = fract(p * 0.1031);
    p += dot(p, p.yzx + 33.33);
    return fract((p.x + p.y) * p.z);
}

float noise3(vec3 p)
{
    vec3 i = floor(p);
    vec3 f = fract(p);
    f = f * f * (3.0 - 2.0 * f);                  // 与 Warp.h 的 smoothstep01 同一个多项式
    ... // 八个角各取一次 hash13，做三线性插值
    return mix(mix(nx00, nx10, f.y), mix(nx01, nx11, f.y), f.z);
}
```

- `hash13` 是"输入一个三维格子坐标、输出一个 $[0,1)$ 伪随机数"的常用写法（`fract` 版），无需纹理。
- `noise3` 是**值噪声**：八个角的哈希值按 `f` 做三线性插值。插值权重用的是 $f(3-2f)$——**和第 2 段 `smoothstep01` 完全同一个多项式**。所以噪声本身也是 C¹ 的，取值在 $[0,1)$，调用方再减 0.5 得到以 0 为中心的抖动。
- 为什么不用噪声纹理：不占显存，也不受"平面投影到船身会拉伸"的影响（值噪声是三维的，切面形状天然贴合体积）。为什么在**物体空间**采样：溶解必须跟着舰体走，世界空间的噪声会让溶解图案随舰体移动而游动。
- 八个 `hash13` 调用在每次片元里，是这个 shader 里最贵的一段；因为它只出现在溶解路径上（且 `discard` 在前），代价可接受。
- 两个函数在 `main` 之后定义，所以文件前面有**前置声明**（`float hash13(vec3 p);` 一类）。这是 GLSL 与 C++ 不同的地方：GLSL 要求先声明后使用，函数定义的先后顺序不能随意。

## 12.3 电流外壳：`warp_shell_ver/frag`

### 12.3.1 顶点着色器

```glsl
vec4 world = model * vec4(aPos, 1.0);
vec3 n = normalize(mat3(model) * aNormal);
world.xyz += n * uShellWorld;          // 沿法线外扩
vWorldPos = world.xyz;
vNormal   = n;
vObjPos   = aPos;                      // 细丝图案绑在舰体上，不随舰体移动而游动
gl_Position = projection * view * world;
```

- **偏移在世界空间做**：物体局部坐标比世界大 2000 倍，在物体空间里定厚度极易搞错量级；而世界空间里"半径的 3%"是一句人话。代价是要先算出世界坐标。
- `vObjPos = aPos` 而不是 `world`：细丝是"爬在舰体上的电流"，必须绑在物体坐标上，否则舰体一动图案就游动。
- **这里有一处需要登记的过时假设**：注释写着"模型矩阵是平移乘旋转乘均匀缩放，所以 `mat3(model) * aNormal` 只差一个正标量"。加进折跃的**轴向拉伸之后，模型矩阵不再是均匀缩放**，正确的法线变换要用 $M^{-\mathsf T}$。后果是外壳在拉伸期间的法线有十几度偏差：费涅尔带随之轻微偏移，外扩方向也略微各向异性（厚度 0.8 世界单位，偏差约 0.2 单位）。它只发生在拉伸与外壳同时活跃的那一小段（约 τ = 0.50 到 0.62），量级很小，所以先登记不改；要修就把 `normalMatrix` 也传进来（两行）。舰体的 PBR 没有这个问题，因为它本来就用 CPU 传来的 `normalMatrix`。

### 12.3.2 片元着色器：细丝

```glsl
float filaments(vec3 q, float t)
{
    float a = sin(q.y * 9.0 + t * 3.0);
    float b = sin((q.x + q.z) * 6.0 - t * 2.2);
    float c = sin(dot(q, vec3(4.0, -7.0, 5.0)) + t * 4.1);
    return 1.0 - pow(abs(a * b * c), 0.35);
}

void main()
{
    vec3 V = normalize(camPos - vWorldPos);
    float fres = pow(1.0 - clamp(dot(vNormal, V), 0.0, 1.0), 3.0);
    vec3  q    = vObjPos / max(uObjRadius, 1e-3);
    float wire = filaments(q, uTime) * smoothstep(0.15, 0.85, fres);
    vec3 col = uShellColor * (fres * 1.6 + wire * 0.9);
    FragColor = vec4(col * uShellStrength, 1.0);
}
```

- **三组平面波相乘再取绝对值**：$\lvert abc\rvert$ 接近 0 的集合是三个"零平面族"的**并集**，于是亮点形成三组走向不同、间距不同的细脊——这正是"电流细丝"该有的样子，而且比三维值噪声便宜（三次 `sin` 对八次哈希）。三条波的法向量 $(0,9,0)$、$(6,0,6)$、$(4,-7,5)$ 的模长互不相等，间距 $\pi/\lvert w\rvert$ 也就互不相等（注意是 $\pi$ 不是 $2\pi$：`sin` 一个周期有两个零点），三条相位速度 $3.0/\lvert w\rvert$、$2.2/\lvert w\rvert$、$4.1/\lvert w\rvert$ 也故意各不相同，图案才不会读起来像周期性的。
- **指数 $0.35<1$ 是"把脊线变细"**：取幂小于 1 会把接近 1 的区域压缩、把接近 0 的区域展宽。换成 $1$ 就得到又粗又糊的条纹。
- 入参 `q` 是**归一化后的物体坐标**（量级约 $\pm1$），所以频率能直接用 $O(10)$ 的常数——这就是要除以 `uObjRadius` 的原因。若忘了除，同一组常数会因为模型尺度（大 2000 倍）变成一片逐像素噪点。
- `smoothstep(0.15, 0.85, fres)` 把细丝限制在**掠射区**：正对镜头那一面若也画满细丝，会糊成一片亮斑，反而读不出"裹住"。
- 最后两个系数 1.6 与 0.9 是"略大于 1"，让峰值能被 bright pass 拾取、进 bloom 晕开；`uShellStrength` 再整体乘上 `wch.c * 2.0`（第 11 段）。
- 外壳的菲涅尔指数取 3，与舰体边缘光的 `rimPower = 3.0` 一致——两者叠在同一处，指数不一致会看出两层轮廓。

# 第 12 段（下）· 线框与全屏闪现的着色器

## 12.4 `warp_wire_*`：用几何着色器画屏幕等宽线框

### 12.4.1 顶点着色器

```glsl
#version 330 core
layout (location = 0) in vec3 aPos;
out vec3 vObjPos;
uniform mat4 projection;
uniform mat4 view;
uniform mat4 model;

void main()
{
    vObjPos = aPos;
    gl_Position = projection * view * model * vec4(aPos, 1.0);
}
```

能省的全省了：没有法线、没有 UV、没有 `normalMatrix`（线框不参与光照，只输出加法颜色）。只留两样东西——物体空间坐标（给生长门用）与裁剪空间位置。这里传进去的 `model` 是**不含拉伸**的 `shipWireModel`（第 11 段），所以骨架永远显示舰体的最终形状。

### 12.4.2 几何着色器：给三个角打重心坐标

```glsl
layout (triangles) in;
layout (triangle_strip, max_vertices = 3) out;

in  vec3 vObjPos[];
out vec3 gBary;
out vec3 gObjPos;

void main()
{
    gBary = vec3(1.0, 0.0, 0.0); gObjPos = vObjPos[0]; gl_Position = gl_in[0].gl_Position; EmitVertex();
    gBary = vec3(0.0, 1.0, 0.0); gObjPos = vObjPos[1]; gl_Position = gl_in[1].gl_Position; EmitVertex();
    gBary = vec3(0.0, 0.0, 1.0); gObjPos = vObjPos[2]; gl_Position = gl_in[2].gl_Position; EmitVertex();
    EndPrimitive();
}
```

- 三个角分别打上 $(1,0,0)$、$(0,1,0)$、$(0,0,1)$。经过光栅器插值后，**三角形边上恰好有一个分量为 0**，而内部三个分量都远离 0。这就是"哪条边"的判据。
- `max_vertices = 3` 配 `triangle_strip`：每个三角形原样输出三个顶点，不增不减。几何着色器在这里只做"挂标签"，不做几何生成——这也意味着它的开销量级与三角形数成正比，而不是与像素数成正比。
- `gObjPos` 逐顶点传出、被插值，所以片元拿到的是**插值后的物体坐标**，生长门是逐片元连续判断的，不是逐面片。
- **为什么不用 `glPolygonMode(GL_LINE)`**：它的线宽由 `glLineWidth` 控制、实现相关（很多驱动只支持 1 像素），也不做抗锯齿。重心坐标加 `fwidth` 能把线宽做成**屏幕空间的解析量**，与距离、与三角形大小都无关，还自带 AA。

### 12.4.3 片元着色器：屏幕等宽与生长门

```glsl
vec3  d    = fwidth(gBary) * uWireWidth;
vec3  s    = smoothstep(vec3(0.0), d, gBary);
float line = 1.0 - min(min(s.x, s.y), s.z);

float g    = (gObjPos.y - uAxisMinY) / max(uAxisMaxY - uAxisMinY, 1e-6);
float gate = 1.0 - smoothstep(uWireGrow - 0.06, uWireGrow, g);

float a = line * gate * uWireAlpha;
if (a <= 0.002) discard;
FragColor = vec4(uWireColor * a, 1.0);
```

- **`fwidth(gBary)` 是关键**：它是重心坐标在屏幕上的变化率，回答"重心坐标变化 1 需要走多少像素"。乘上 `uWireWidth`（约 1.5 像素）得到 `d`，于是 `smoothstep(0, d, gBary)` 在"离边 d 个重心单位"内做过渡，换算到屏幕就是**固定像素宽**的线。同一套代码在近处与远处给出同样的视觉效果，而且 `smoothstep` 自带解析抗锯齿，所以 1k 面数也不会闪成噪点。
- `line = 1 - min(min(s.x,s.y),s.z)`：三个分量里最小的那个对应"离最近的那条边"。在三角形内部三个 `s` 都是 1，`min` 也是 1，于是 `line = 0`——**内部不画，只画边**。这就是"线框"的全部几何定义，不多不少。
- `gate` 是生长门：`g < uWireGrow - 0.06` 处为 1，`g > uWireGrow` 处为 0，中间 0.06 宽是软边。`uWireGrow` 由 `wireGrow(τ)` 提供（第 7 段），因此"自艏向艉画出来"这件事完全由时间线决定，着色器不含任何时间逻辑。
- `uWireAlpha` 由 `wireAlpha(τ)` 提供。**位置与强度在这里彻底分家**：位置只前进（单调），强度负责整体明暗与末段淡出。第 7 段那六次返工最后收敛到的就是这个结构。
- `if (a <= 0.002) discard;`：对加法混合来说 `a` 就是"要加多少"，加 0 与不画等价；丢掉这些片元省下混合带宽。它还有一个隐性好处——没生长到的区域完全不进混合，所以线框不会在暗处留一层灰雾。
- **最容易写错的一行**是最后一行：`FragColor = vec4(uWireColor * a, 1.0)`。颜色里已经乘过 `a`，而 alpha 通道写的是 1.0。因为混合方式是 `GL_ONE, GL_ONE`（加法），着色器输出的是"要加的量"而不是"带透明度的颜色"。若按常规 alpha 混合的思路把 `a` 写进 alpha、颜色不乘，线框会变成满亮度的实心亮面。

## 12.5 `warp_flash_*`：全屏 quad

### 12.5.1 顶点着色器

```glsl
layout (location = 0) in vec2 aPos;
out vec2 vNDC;

void main()
{
    vNDC = aPos;
    gl_Position = vec4(aPos, 0.0, 1.0);
}
```

- `quadVAO` 的属性 0 本身就是 NDC 坐标（$-1$ 到 $1$），所以 `gl_Position` 直接写 `vec4(aPos, 0, 1)`，**一个矩阵都不需要**。这与大气全屏 pass 是同一套约定。
- 它把 `aPos` 直接当"屏幕位置"传给片元，于是片元既不需要分辨率 uniform 也不需要 `gl_FragCoord`——这正是 cpp 里那个 `flashCenter`（NDC）能直接和 `vNDC` 相减的原因。

### 12.5.2 片元着色器

```glsl
uniform float uFlash;        // 闪现强度（已按模式门控，模式 1/2 传 0）
uniform float uFlashBase;    // 整屏基底亮度
uniform float uFlashCore;    // 中心附加亮度
uniform vec2  uFlashCenter;  // 舰体的屏幕位置（NDC）

void main()
{
    vec2  d    = vNDC - uFlashCenter;
    float core = 1.0 / (1.0 + 6.0 * dot(d, d));
    vec3  add  = vec3(uFlashBase + uFlashCore * core) * uFlash;
    FragColor  = vec4(add, 1.0);
}
```

- `core` 是洛伦兹型衰减：$d=0$ 处为 1，半屏处（$|d|\approx0.7$）约 0.14。它**只给 bloom 一个圆心**，让晕开的方向从舰体位置向外，不是拿来替代基底。
- **基底 `uFlashBase` 是硬性要求**，不能改成"中心亮、边缘暗"的径向渐变。理由写在这份着色器的注释里，也是它存在的唯一理由：跟随模式下行星的角位移可达数十度（计划书 §4.2 推论 2），**画面的边缘也必须被压到白**，否则边缘会露出背景的跳变。改成径向渐变就等于把遮蔽做成了一个圈，圈外的世界照旧会跳。
- `uFlash` 已经在 cpp 里乘过 `camGate`，模式 1/2 时是 0，`if (flashAmount > 0.0f)` 直接不进这个 pass，所以着色器里**不需要再判模式**。判据只写一处（第 10 段）。
- 两个默认值（6 与 10）都远高于 bright pass 阈值（约 1.0），所以峰值帧必然整屏过曝并进 bloom——与 `uWhiteK = 6.0` 是同一个套路：**要"发光"就必须给出超过 1 的值**，而不是给出一个漂亮的白色。
- 同样要注意输出语义：加法混合下输出的是"要加多少"，alpha 写 1.0 即可。
